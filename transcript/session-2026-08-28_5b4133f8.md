## Where they live

In-engine cutscenes are **not a separate format**. They are `SCPTDATA/*.SCX` — the same scene files the dialogue staging uses — with four chunks doing the work, plus a world script acting as director:

| piece | where | what it contributes |
|---|---|---|
| the "director" programs | SCX **chunk 2**, 100-byte objects | one object = one beat, a list of functions run per frame |
| body animation | **chunk 1** `.3DA` clips | `Script_SelectBodyAnimation` (+ root motion → `Actor_MoveBy`) |
| object motion | **chunk 0** `.3dp` paths | `Script_MoveObjectOnPath` — 4841 calls, the most-used function of the 17 |
| **the camera** | **chunk 10**, the *camera editings* | keyframed cuts, `Cam_PlayEditing` |
| sound | the sibling `*.sfx` | the loader takes `x.scx` → `x.sfx`; the engine's own string is `"sfx for cin"` |

## How the camera is taken over

`Script_PlayScript` (CLEAN, `readable/src/17_script.c:631`) does it at the top of every object's tick: if the object has an editing linked (bytes `+94..97`, wired by `Script_LinkCamEditing`), it samples it at the object's own program clock and calls `Scene_SetActiveCamera` — and **skips the object's own camera functions** while it drives. Editing slots advance as each duration expires.

## Why it doesn't wait for the player

That's the `.wait` half of the `scx.play` family (ops 58/60/46), and the loop is closed in code:

1. the handler starts the object, registers the script's slot, and writes **4** into the script's status word (`mov word ptr [esi+16h], 4`) — `Script_Execute` only runs while status is 1, so the world script stops;
2. every frame the engine scans the 32-slot table at `dword_910508` and, for each waiting slot, calls `ScriptObject_IsBusy`;
3. when the object's program has ended it raises **event 3**, and `Game_HandleEvent` case 3 sets the status back to 1 (`01_file.c:1188`).

So the resume is driven by the animation program finishing. Input is never consulted. `player.anim.hold` takes the body off the walker for the duration.

## Why the translation layer mostly doesn't matter

The plan already commits to this, before any of it was on the table:

> **Diff decisions, not numbers.** The original computes on the x87 stack with 80-bit intermediates; any portable replica will use doubles or SSE and drift in the low bits immediately. A trace comparison must therefore be at the level of *what the game decided* — which script ran, which opcode with which operand, which state bit changed, which dialog started, which state a channel entered — with floats compared under a tolerance and never for equality.

A 32-on-64 translator introduces exactly the same *class* of discrepancy that a portable replica does — low bits of x87 results. So it doesn't add a new risk; it lands inside the tolerance the design already carries.

More concretely, tier the trace by what it's made of:

| trace | made of | affected by translation? |
