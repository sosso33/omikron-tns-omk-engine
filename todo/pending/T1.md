## 1. What changed

* **Division truncates** (`divTrunc`, replacing `divFloor`). Op 34's handler at
  `0x402750` pops the top into `eax`, the word under it into `edi`, and runs
  `cdq; idiv edi`; `var.div` (22, `0x402390`) runs `Var_Get(var)` over the
  popped top the same way. x86 `idiv` truncates toward zero. The two guards are
  the PORT's, labelled in the code: `b == 0` returns 0 and `INT_MIN / -1`
  returns the wrapped negation — both raise #DE in the engine, a crash rather
  than a decision.
* **The shared fetch on every 16-bit field.** `push.i16` (8, `0x401D70`),
  the variable index of 14/15/16 (`0x401F70`/`0x401FE0`/`0x402070`), both
  fields of 17 (`0x402110`) and both of 71 (`0x403950`) now go through
  `fetch16`. **Correction to the brief:** op 15's VALUE goes through the fetch
  as well — its handler runs `cmp ax,0FFFFh; test ah,40h; movsx eax, word ptr
  [ecx+eax*2+2]` a second time for the value — so a `set.var.i16` value can
  be indirect. Only 14's int8 and 16's int32 are read raw. The `interp.h`
  comment that named 4, 6, 10, 18, 42 as the only fetchers is rewritten.
* **The fetch's index is offset by one word — and that changes what issue 20
  says is pushed.** Every fetching handler reads
  `movsx eax, word ptr [block + eax*2 + 2]`: index 0 is the block's SECOND
  word. `Message_RunHandlers` (`0x00409420`) fills the 8-byte block as
  `args[0] = message id, args[1] = sender`, so `push.i16 0x4000` pushes the
  **sender**, not the message id. The corpus settles it independently: every
  one of the 59 shipped operands with the bit (see §4) is
  `push.i8/i16 <constant>; push.i16 0x4000; eq; jmp_if_false`, with constants
  such as 173, 346, 410 (actor ids, under message 3) and 3, 100, 10, 88
  (object ids, under message 4) — a script subscribed to message 3 has
  nothing to learn from the number 3. `tools/sim`'s docstring already says
  "offset by one element"; the port's `fetch16` now does `params_[i + 1]`, and
  `setParams` is documented as taking the block **as the engine fills it**,
  `{message id, sender}`. T2's message dispatch should pass exactly that.
* **`var.set.random` (120) implemented.** The real handler is at `0x405480`
  (the pre-split block is the function after it — CLAUDE.md §1's trap):
  three fetches — lo, hi, VARIABLE — then, unless the dry-run flag is set,
  `Var_Set(var, Random_NoRepeat(lo, hi))`. `Random_NoRepeat` (`0x0041D6B0`,
  `readable/src/05_sys.c`) returns lo when lo == hi and otherwise redraws
  `lo + rand() % (hi - lo + 1)` until it differs from `dword_4E7E8C`, the
  previous result. Ported as `Interpreter::randomNoRepeat` over a
  **process-global** xorshift32 and a process-global last draw — global
  because `rand()`'s seed and `dword_4E7E8C` are: the passer-by line one
  script drew is the one the next script cannot draw. `seedRandom(s)` is
  static, sets the state and forgets the last draw, so a seeded run is one
  fixed sequence (`o3de/particles.h`'s argument: WHERE randomness enters is
  ported, not which numbers). `hi < lo` returns lo — the port's choice where
  the engine takes a zero or negative modulus. The call is recorded as
  `{lo, hi, var}` (resolved) when `record_ && !recordAll_`, like 64/65/71.
* **`setRandomWrites(bool)`**, default on. Off, 120 records and does not
  write — the fourth "compare like with like" switch, and §3 says why it is
  needed.

## 4. Findings beyond the brief

* **`set.var.i32` (16): the table says 5 operand bytes, the handler reads 6.**
  `0x402070` fetches the 2-byte variable, then `mov eax, esi; add esi, 4` and
  assembles four bytes (`mov cl,[eax]; dh,[eax+1]; inc eax; inc eax;
  dl,[eax]; shl 16; dl,[eax+1]; shl 24`). `tables/vm_opcodes.json` row 16:
  `length 5, table_says 5, corrected false`; `dialog_disasm.LEN_FIX` has no
  entry. **0 shipped world scripts use op 16**, so the corpus cannot see it,
  and the probe shows it: the port reads the four value bytes (var5 = -7) and
  then advances by the table's 5, landing on the value's last byte as an
  opcode. For **T8** (tables + `LEN_FIX`): add `16: 6`. The interpreter needs
  no change once the table is right.
* **Count of indirect operands: 59, not 22.** Deduplicated by
  (archive, chunk, pc) over `tools/sim.world_scripts()`, all 59 are
  `push.i16 0x4000` in seven scripts — AREA 2 (msg 3), 61 (3), 141 (3),
  144 (2); SCENE 56 (3); GLOBAL records 0 and 8 (4) — each immediately
  compared against a constant with `eq; jmp_if_false`. The 22 in issue 20 may
  be a different dedupe; the method here is in the numbers above. No other
  opcode carries the bit anywhere (the sweep's DB identity with writes off is
  the corroboration: had one existed, the resolved index would have moved a
  write).
* **Op 34 `div` has 0 sites in the world corpus** (74 of `var.div`), so the
  truncation fix can only ever be tested by the probe.
* **`recordAll_` narration is still the raw halves.** With the bit set the
  engine's `Dbg_LogTagged` logs the resolved value (`push edi` after the
  fetch); the narration here records `0x4000`. No trace reaches a message
  handler today (issue 8), so nothing compares it yet. Worth a line when T2
  dispatches messages live.
* **`FILE_FORMATS.md` line ~819** says the handler runs "with
  `{message id, sender}` as parameters" — true of the block, but the only
  parameter a script can reach through operand `0x4000` is the sender. Doc
  paragraph in §7.
