## 1. What each handler does, quoted

All three read with `python3 tools/asmfn.py --op N`, which anchors on the
listing's own labels at the address `tables/vm_opcodes.json` names — not from
`clean/_vmhandlers.json`, whose blocks can be the wrong function (CLAUDE.md
§1). Each block here is bounded exactly by the next handler's entry, so the
trap does not bite.

### 89 `player.move.wait` — 0x004043F0 (548 sites)

```
push    esi
mov     esi, [esp+8]                 ; the context
...                                  ; ONE shared fetch -> ecx (the ADDRESSES id)
mov     [esi+0Ch], eax               ; the pc, advanced by 2
loc_404422:
mov     eax, dword_6A05E0            ; the dry-run flag
or      byte ptr [esi+28h], 10h      ; ctx+40 |= 0x10 (the Script_Run abort bit)
test    eax, eax
jnz     short loc_404444
xor     edx, edx
mov     dl, [esi+1Eh]                ; ctx+30 - the context's TABLE INDEX
push    edx
push    ecx
call    sub_41B6F0                   ; Player_GoToMove(address, ctx+30)
add     esp, 8
mov     word ptr [esi+16h], 4        ; <- the park
loc_404444:
pop     esi
retn
```

### 63 `player.move` — 0x00403730 (312 sites)

**The identical handler**, instruction for instruction, with two differences:

```
push    0FFFFFFFFh                   ; -1 where 89 pushes ctx+30
push    ecx
call    sub_41B6F0
add     esp, 8
                                     ; ...and NO `mov word ptr [esi+16h], 4`
```

So the pair is exactly the shape `scx.play.wait` / `scx.play` has: hand the
mover your own slot and it will report back, or pass −1 and run on. **63 must
never park**, and it must still carry its address so a Session can start the
move.

## 2. What changed in the interpreter

`RunStatus` gains **`MoveWait`** and **`FightWait`**; 126 joins 96 on the
existing **`CameraWait`**, because it is one status word and one release event
— what distinguishes them is now in the result, not in the enum.

`RunResult` gains:

| field | set by | why it must be there |
|---|---|---|
| `moveAddress` | 89 | the Session has to START the walk; the interpreter only reports the decision |
| `fightOpponent`, `fightCamTravel` | 62 | the opponent, and `max(field 1, 0)` exactly as the `jge` writes it |
| `camWaitOp` (96 or 126, 0 = neither) | 96, 126 | **the 0-travel difference**; a caller reading only `camTravel` would cut where the engine holds |
| `camAddress` (−1 for 96) | 126 | `Address_Find(field 1)` is the camera's SUBJECT, where 96 uses the player |

Two new switches, `setMoveWaitSuspends` and `setFightWaitSuspends`, **both
default off**, for the same reason as the three beside them: the corpus sweep
compares against `tools/sim`, whose standalone VM stubs all of these, and 548 +
108 shipped sites would otherwise make the two disagree about something neither
models. 126 is gated on the existing `setCameraWaitSuspends`, which is also off
by default and which `backends/sdl/play.cpp` turns on.

`setFightWaitSuspends`'s comment carries the one warning a caller needs:
**nothing in the pump can release status 3**, so a Session that parks here with
no fight runtime parks for ever. That is the engine's shape, but a replica must
leave it off rather than invent a deadlock — the same rule `ObjectWait` already
follows by refusing to park on a program that never started.

**63 needed no code at all.** The generic stub recorder already emits
`63:<address>` — one field, because the table gives it 2 operand bytes — which
is everything a Session needs to start an unheld move. The probe asserts that
with *every* parking switch on it still reaches `end`.

## 5. The op 62 operand-length finding — for the coordinator, NOT applied here

**`tables/vm_opcodes.json` gives opcode 62 four operand bytes and the handler
reads six.** Three shared fetches in a straight line at 0x004035D0, no branch,
each writing `[esi+0Ch]` back; `tools/vm_oplen.py` prints `62 : 4 -> 6` and has
all along (it is one of the 21 disagreements, and not one of the 20 that have
been corrected).

The corpus adjudicates, exactly the way it did for op 103 (CLAUDE.md §1):

| 62's length | slots | failures | instructions | sites | `dbg.dump_ctx` | `dbg.dump_code` | `nop` |
|---|---|---|---|---|---|---|---|
| 4 (the table) | 5785 | 0 | 58644 | 108 | 149 | 37 | 39 |
| 6 (the handler) | 5785 | 0 | 58428 | 108 | **5** | **1** | **3** |

216 instructions vanish — 144 + 36 + 36 — which is **exactly two per site over
108 sites**, and at length 4 the opcode immediately after every single
`fight.begin` is a 0, a 1 or a 2 (36 each). Those are the two surplus operand
bytes decoding as inert zero-operand opcodes.

**That inertness is why nothing has failed and why this is not urgent.** The
port's pc is two bytes short of the engine's for two harmless no-ops and then
resynchronises, so no behaviour differs — the cost is 216 phantom
announcements in any trace, and the third operand (`Fight_Begin`'s own second
argument, which is 0/1/2 across the shipped sites) being unreachable. While the
table says 4, `FightWait` carries two fields; at 6 it can carry three.

Correcting it touches `tables/vm_opcodes.json` (via `tools/exetables.py`'s
correction list), `tools/dialog_disasm.LEN_FIX` and any doc quoting 58644 —
**all in one step**, since `engine: execute` compares the two sides. Out of
this task's file scope; flagged rather than done, and asserted in §3 so it
cannot be lost.

Two smaller ones found on the way, both **unreachable in the shipped data** and
therefore left alone:

* **96 parks on a NEGATIVE travel and the port does not.** The guard is
  `test ebp,ebp; jz` — zero, not "not positive" — while `interp.cpp` has
  `travel > 0`. No shipped site is affected: 96's field 1 is 20..500 over 1024
  sites, never 0 and never negative.
* **96 HALVES its travel when the camera record's `+0x1A` is 4**
  (`cmp word_4E6C64, 4; ... sar eax, 1`). The port does not model it. It needs
  the camera record, so it belongs with whoever owns `applyCamera`.

### 6c. `area.cpp` — the two releases

```cpp
// `Game_HandleEvent` case 3, the move half. The object half is
// `transitionObjectEnded`; this is the same event with a different raiser.
void Session::playerMoveEnded(int ctx) {
    if (ctx < 0 || ctx >= kContextSlots) return;
    Ctx* c = ctxs_[static_cast<std::size_t>(ctx)].get();
    if (!c) return;                                  // `if (!v2) return 1;`
    if (c->status != 4) return;                      // case 3's own test
    c->waitingForMove = -1;
    c->status = 1;                                   // runs again this pump
}

// `Game_HandleEvent` case 2. The FIRST context at 3, and the bank reload
// regardless - the port models the status half; the .CTL reload belongs to
// whoever owns the player's channel and is named here rather than silently
// skipped.
void Session::fightEnded() {
    for (int i = 0; i < kContextSlots; ++i) {
        Ctx* c = ctxs_[static_cast<std::size_t>(i)].get();
        if (!c || c->status != 3) continue;
        c->fightOpponent = -1;
        c->status = 1;
        break;                                       // the FIRST one only
    }
}

int Session::fightingWith() const {
    for (const auto& c : ctxs_)
        if (c && c->status == 3) return c->fightOpponent;
    return -1;
}
```

### 6e. `area.cpp` — `Session::execute`'s switch, two new arms

### 6h. The two hooks the arms call

`startPlayerMove(int addressId, int ctx)` and `beginFight(int opponentId)` are
the Session's boundary to the actor runtime, in the shape `placeActorAt`
already has. Minimal honest bodies, both returning **false when there is
nothing that could ever end the thing they start** — which is what keeps the
park out of a deadlock:

```cpp
// `Player_GoToMove` (sub_41B6F0): walk the player to an ADDRESSES record, and
// report to context `ctx` when he arrives. Only the address resolution is
// ported; the walk itself belongs to the actor runtime, and with none attached
// this returns false and the caller runs on.
bool Session::startPlayerMove(int addressId, int ctx) {
    if (!moveHook_) return false;
    const Address* a = findAddress(addressId);       // as `placeActorAt` does
    if (!a) return false;
    return moveHook_->goToAddress(*a, ctx);
}

// `Fight_Begin` (sub_41A3B0). No fight runtime -> false, and the script runs
// on: status 3 is released only by `fightEnded`, so parking without one would
// stop the game.
bool Session::beginFight(int opponentId) {
    return fightHook_ && fightHook_->begin(opponentId);
}
```

## 9. What could not be established

* **Nothing here has an oracle, and none is reachable** — the rig sees only
  what a handler narrates, and these three narrate nothing usable. Every claim
  is the handler's assembly plus a corpus shape.
* **126's unconditional park is not corpus-visible.** All 84 sites travel 20
  frames, so only the missing `test ebp,ebp` establishes it. Ported from the

  that the opcode orders a move and parks, not how the walk is executed; the
