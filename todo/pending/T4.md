## 1. What changed, and the engine line each transcribes

### Issue 5 — the activate dedupe

`Script_QueueAction` (0x004063D0) is now transcribed as `World::queueAction`,
including the arm nobody would guess: a **full** FIFO stores nothing and still
returns 1.

```
v2 = count(+28);
if (v2 >= 4)  printf("%d\n", v2);          // full: nothing stored, returns 1
else {
    for (i = 0; i < 4; ++i)
        if (a2 == fifo[i] && a2 == 2) return 0;
    if (a2 == current(+32) && a2 == 2) return 0;
    fifo[v2] = a2; ++count;
}
return 1;
```

The second half of that rule needs `+32`, the context's **current** action, and
`+32` is not write-only: `Script_Execute`'s tail (0x00406460, the `LABEL_8`
arm) clears it —

```
if (u32(a1,32) != 1 && u32(a1,32) == 2 && !u16(a1,22)) { --dword_4E6B20; ...; u32(a1,32) = 0; }
```

— *only* for action 2, and *only* once the status word is back to 0. So the
dedupe is **"no second activate while the first has not finished"**, not "one
activate ever": a parked activate (a camera move, a screen, a conversation)
holds the refusal open, and one that reaches `end` releases it in the same
`Script_Execute` call, because the `end` handler drops the status and the loop
exits through `goto LABEL_8`.

Ported as `Context::act` (the field), `World::queueAction` (the refusal) and
the clear in `World::pump`, placed in **both** the "not running" path and the
finish path — the engine reaches it from either.

`activatesQueued()` is the engine's own `dword_4E6B20`; `activatesRefused()`
counts the returns of 0.

### Issue 5 — the one-shot bit, **with a correction to the issue text**

`Zone::oneShot()` reads bit 15 of the record's `+64`; `Zone::stateBit()` keeps
the mask, because `Zone_StateBit` (0x0040D500) indexes the save bitmap with
`(id & 0x7FFF) / 8`. **37 of the 4558 shipped zones carry it** (AREA 146, 178,
179, 181 hold most of them).

Issue 5 says the bit "puts the slot in state 5, which the next pump frees (leave
+ free) **whether or not the player is still inside**". The assembly says
otherwise, and this is the one place where the ported behaviour is not what the
issue asked for:

* `Script_Pump` state 2 (`sub_407DC0`, `loc_407FBE`) does
  `test byte ptr [esi+0Bh], 80h` / `mov word ptr [esi+8], 5` — the slot goes to
  state 5, as the issue says;
* but `Game_HandleEvent` case 7 maps **state 5 back to 4** (`if (v22[4] != 5)
  return 1; v22[4] = 4;`), and pump **case 4** maps 4 back to 5
  (`loc_407FD4: mov word ptr [esi+8], 5`);
* and case 7 is raised by `Actor_ScanZones` (0x00467770) **every frame** the
  player is inside the quad and inside the arc — it is not an edge;
* and the pump runs **before** the actor tick: `Script_Pump(1)` is
  `readable/src/05_sys.c:2107` (`dword_4E9740 &= sub_408410(1)`) and
  `Actors_TickAll()` is `:2178`, both inside `Game_Tick`.

So 4 and 5 ping-pong for as long as the player stands there. The bit does not
free the zone early — it **latches the slot out of the press cycle**, and the
free happens on leaving like any other zone (state 5 with no event 7 falls into
the shared `cases 3,5` body). Ported as `Context::spent`.

What the latch is *for* is exactly the gap the `LABEL_8` clear opens: an
ordinary zone whose activate script reaches `end` can be activated again by the
next press, and a one-shot one cannot. That is measured below (zone 1466 stays
at 5 activates; one-shot zone 35141 goes from 5 to 1).

**Coordinator: issue 5's last sentence needs amending.**

### Issue 9 — the touch camera

`World::step` now follows `Actor_ScanZones`'s order — containment first, the
arc second — so a zone that is touched but not faced is still seen. Every
contained zone counts as event 8; when its `+66` is not −1 the step records
`Camera_FindWorld`'s argument, last one winning, because each event 8
overwrites the same request block (`dword_4E6C40`).

New: `touchedCamera()` (the last camera a touch asked for **this step**, −1 if

### Issue 13 — a parked script resumes

`Context` now owns its `Interpreter` (a `unique_ptr`, so the **stack** survives)
plus `entry` / `pc` / `started`, and `World::pump` calls
`vm->resume(code_, pc)` on a context that has already started. **Only `End` and
the error statuses finish an action**; every park keeps the context's status at
1, which is what stops `Script_ProcessActions` arming the next action
underneath it.

Per status, mirroring `Session::Ctx` in `area.h` so the two agree:

| status | what holds it | what releases it |
|---|---|---|
| `UiOpen` (6) | `waitingForUi` | nothing — a PERSON answers, and `World` has no screens |
| `CameraWait` (7) | `waitingForCamera`, a **countdown in frames** | the move's own length (`r.camTravel`) |
| `ObjectWait` (4) | — | resumes next pump: `World` has no resident scene, so the engine would have nothing to release it either |
| `Suspended` | — | the scheduler, i.e. next pump |
| `Dialog` | `dialogState_ = 3` | `endDialog()` |

`Dialog` is the odd one: the handler writes **no** status, so the context stays
running with its pc past the operand and the *pump* stops instead —
`Script_Pump` opens `if (g_DialogState != 1) return 1;`. `World::step` now
honours that (after the touch scan, which is in the actor tick and is not part
of the pump), and `Script_ProcessActions`'s own `if (g_DialogState == 3)
return` is in `World::process`. `dialogOpen()` / `endDialog()` are the caller's
handle on it.

`setCameraWait(bool)` / `setObjectWait(bool)` mirror `Session`'s pair and
default **off**, for the reason `Interpreter::setCameraWaitSuspends` gives — so
`walk_zone` and `launch_scene` are bit-for-bit unaffected.

## 5. Doc text

For `docs/SCRIPT_VM.md`, wherever the status/resume map lands (T10 owns that
file, so this is text to fold in rather than an edit):

> **An action is not over when its script returns.** `Script_ProcessActions`
> dequeues one action, points the context at the matching script slot and sets
> the status word to 1; `Script_Execute` loops `while (status == 1)`. A handler
> that PARKS its caller writes that word — 4 for a waiting `scx.play*`, 6 for
> `ui.open`, 7 for `camera.set.wait` — and the loop drops out with the pc and
> the stack intact. `Script_ProcessActions` then refuses to arm anything else
> for that context (`if (status) return`), so the queued actions wait behind
> the parked script rather than overtaking it, and the pump resumes it on a
> later frame. `dialog.start` is the exception that proves it: its handler
> writes **no** status and `Script_Execute` simply returns, leaving the context
> at 1 — what stops the world is `Script_Pump`'s own first line,
> `if (g_DialogState != 1) return 1;`.
>
> Only `end` ends an action. That is also what makes the activate dedupe work:
> `Script_QueueAction(ctx, 2)` refuses while `+32` reads 2, and
> `Script_Execute`'s tail clears `+32` only when an activate finishes with the
> status back to 0. Leaning on the action button inside a trigger therefore
> runs its activate script once and waits for it, however long it parks — and
> runs it *again* on the next press once it has ended, unless the zone carries
> the one-shot bit.

For `docs/FILE_FORMATS.md` §5b2b, beside the zone record's `+64`/`+66`:

> `+64` is the ZONES.TAG id **and a flag**. Bit 15 is not part of the id —
> `Zone_StateBit` (0x0040D500) indexes the save bitmap with `(id & 0x7FFF) / 8`
> — and `Script_Pump` tests it as `byte ptr [slot+0Bh] & 0x80` right after
> queueing an activate, latching the prompt slot into states 4/5 so it never
> re-enters the press cycle. It does **not** free the zone while the player is
> still standing in it: `Game_HandleEvent` case 7 maps 5 back to 4 every frame
> `Actor_ScanZones` still finds the player armed, and the pump's case 4 maps it
> back to 5, so the pair ping-pong until the player leaves and the ordinary
> leave-then-free path takes over. **37 of the 4558 shipped zones carry it.**
>
> `+66` is a world camera, `-1` for none. `Actor_ScanZones` raises event 8 for
> every zone whose quad contains the player — **before** the facing test — and
> `Game_HandleEvent` case 8 hands a non-`-1` `+66` to `Camera_FindWorld` and
> points the camera at the request block. **54 zones carry one, over 40
> distinct cameras.**

## 6. What I could not do

* **The pump's inline `Script_Run` is not modelled.** `Script_Pump` state 2
  runs the context's *current* script inline before queueing the activate —
  `Script_Run` (0x004060B0) normally, `Script_RunToOpcode75` (0x00406120) while
  the player holds an object — and both are **dry runs** (`g_ScriptDryRun = 1`;
  every handler consumes its operands and returns without writing). `World` has
  no held-object state and no dry-run mode, so it skips this. It matters for
  issue 7 (the unconsumed press, `dword_4E66B8`/message 26) rather than for
  anything here — but note that the one-shot latch's *other* effect is to stop
  those inline runs happening on later presses, and that half is unported.
* **`Script_Pump`'s slot state machine is still implicit.** `World` derives
  "armed" from the position and facing each step instead of keeping the 16
  prompt slots with their states 0..5 and letting `Game_HandleEvent` case 7
  drive them. The two agree on everything measured here, and the ping-pong
  above is modelled by its *effect* (`Context::spent`), not by the states. The
  one place they can differ is a zone entered *during* a conversation: the
  engine fills the slot then (case 7 is not in the pump) and acts on it when
  the conversation closes; `World` defers the fill, so a player who walks
  through and out again mid-conversation loses the enter script. Labelled in
  `world.cpp`.
* **`ObjectWait` resumes next pump rather than parking**, because `World` has
  no resident scene to run a program — the same call `area.cpp` makes, for the
  same reason. `setObjectWait(true)` only changes whether the interpreter
  *reports* the park.
* **Nothing releases a `ui.open` park**, by design: a person answers it. The
  context is listed by `parked()` and sits there.
* **The `Dialog` gate is context-local plus a pump stop**; `World` has no
  dialogue runtime, so `endDialog()` is the caller's. Issue 2 and issue 10 own
  the rest of that.
* **`verify.py` was not run** (task rule), so the check above is written but
  unexecuted as a `verify.py` check — its expected tuple is transcribed from an
  actual `zone_probe` run, and the failing "before" tuple from an actual
  pre-fix run.
* **No golden trace can adjudicate any of this.** `Script_QueueAction`,
  `Script_Pump` and `Script_Execute` announce nothing to `Dbg_LogTagged`; only
  the opcodes the resumed script goes on to execute do. So the standard here is
  DATA-CONSTRAINED + assembly-transcribed, not engine-verified — which is worth
  saying because the resume changes *when* announcements happen, and that is
  the one part a capture could eventually check.
