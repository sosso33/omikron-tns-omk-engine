## 1. What was added, and what each transcribes

### Object lists (issue 29)

A list is `capacity` int16 ids terminated by `-1`, and no count is stored:
`ObjectList_SetCapacity` (0x00409B00) recovers it by scanning for the
terminator, capped at the capacity. That scan is `listCount`.

| method | engine |
|---|---|
| `listCount(list)` | `ObjectList_SetCapacity` 0x00409B00 |
| `listAt(list, i)` | — (a reader for probes and checks) |
| `listHas(list, id)` | op 49 `var.set.has_object` 0x0040A440 |
| `listAdd(list, id, noDuplicate)` | op 50 `inventory.add` 0x0040A4D0 → `ObjectList_InsertFront` 0x00409CB0 |
| `listRefusesDuplicates(list)` | the 50 handler's `cmp edi,3 / cmp edi,2` arm |
| `listRemove(list, id)` | op 51 `inventory.remove` 0x0040A5A0 |
| `listRemoveAll(list, id)` | op 52 `inventory.remove_all` 0x0040A6A0, main path |
| `listClear(list)` | **nothing** — port-side only, and labelled as such |

Two things about `listAdd` are not what "add" suggests, and both are the
engine's:

* **it inserts at the FRONT.** `ObjectList_InsertFront` is
  `memmove(base + 2, base, 2*capacity - 2)` then `base[0] = id`, so the newest
  item is index 0 and the terminator slides up one slot;
* **it refuses when the list is full** — `if (capacity == count) return 0` is
  that function's first line, which is also what makes dropping the last slot
  safe.

`noDuplicate` is per LIST, not per opcode: the 50 handler scans for the id only
when the list selector is 2 or 3.

Not modelled, deliberately: `Inventory_Insert` (0x004098E0)'s kind arithmetic,
which merges ammunition and money into an existing slot's *quantity* (kinds
2..6 and 7..11) instead of taking a slot. That lives in the 56-byte parallel
array `dword_69BD68` — a runtime cache copied out of `IAM\OBJECT` on insert,
not part of the DB and not saved — which the port rebuilds from the object
table by id. Only the stored id array is state, and only it is modelled.

### Prop state (issue 30)

`propState` / `propStateBits` / `setPropState` over `StateArray::PropState`,
from `ObjectState_Get` (0x0040B010) and `ObjectState_Set` (0x0040AFC0).

`propState` transcribes the getter **including its sign extension**, which is a
property of the shipped build and not a decompiler artefact — the assembly is

```asm
movsx   eax, byte ptr [eax+edx]   ; the byte, SIGNED
mov     dl, 3
shl     dl, cl                    ; cl = 2*(i%4); dl = 0xC0 at i%4 == 3
movsx   ecx, dl                   ; ... sign-extended too
and     eax, ecx
mov     cl, bl
shl     cl, 1
sar     eax, cl                   ; ARITHMETIC shift
```

so for `index % 4 == 3` state 3 reads back as **−1** and state 2 as **−2**.
Nothing in the game can see it: every shipped consumer masks the low byte
(`test al,1` in op 68/76, `or al,2` before the setter, `& 1` / `& 2` in
`Scene_LoadProps`). `propStateBits` is the plain 0..3 for tools and checks.

### The clock and the script timer (issue 37)

Neither is in the 8192-byte image — they are engine globals (`g_ClockTime`
= `dword_4C2BD0`, `g_ClockDay`, and the timer's `dword_930760/64/68`) — so
`raw()`, `walk()` and the save round trip are untouched. They are on
`GameState` because they are game state a script reads and writes, and because
the clock is the only thing the timer counts against. The save carries day and
time *beside* the DB (`savefile.h`'s 32 + 4 + 4 header); the timer is not saved
at all.

**The clock's unit is a MILLISECOND, and that is derived, not assumed.**
`Clock_Tick` (0x0041E600) accumulates the frame delta — which `Game_Frame` sets
to `30/fps`, so 1.0 is 1/30 s at any frame rate — and every 5.0 of those
(1/6 s) adds **166**. That is 996 units a real second. Two independent
corroborations agree: `Timer_Format` divides the same quantity by 1000 for
seconds and takes `% 1000 / 10` for hundredths, and op 113 multiplies its
operand by 1000 — so `timer.set 900` is the Tetra bombs' 15 minutes, and a
3600000-unit day is one real hour of play mapped onto 21 game hours.

Methods: `clock/setClock/clockDay/setClockDay/clockTick`, and
`timerReset/timerStop/timerStart/timerSet/timerMode/timerElapsed/timerCheckExpiry`
with a `TimerFlag` enum (`kTimerStopped` 1, `kTimerCountdown` 4,
`kTimerVisible` 8, `kTimerExpired` 0x10). `timerElapsed` returns whether the
timer was running, which op 115 ignores — it stores the value either way — and
does **not** apply the countdown flag: only `Timer_Format`'s display does.

## 2. THE FINDING: `tables/vm_opcodes.json` has ops 111 and 112 INVERTED

The table names 111 `timer.start` and 112 `timer.stop`. The mechanism is the
other way round.

Neither of the two functions the handlers jump to has a `proc` label
(CLAUDE.md §1's trap — they are reached only by a tail `jmp`), so this is read
out of `Runtime.exe.asm` at the addresses the handlers name:

```
op 110  0x00405340 -> sub_41E260   flags = 1                     (unnamed; 0 sites)
op 111  0x00405350 -> loc_41E2B0   requires !(flags & 1); flags |= 1
op 112  0x00405360 -> loc_41E2D0   requires  (flags & 1);
                                   g_TimerStart = g_ClockTime; flags &= ~0x11
```

so **111 halts and 112 runs**. Three things settle it beyond the assembly:

1. `Timer_SetValue` (0x0041E270) and `Timer_SetMode` (0x0041E290) both bail
   unless `flags & 1`, so the configure pair can only ever precede the start;
2. the shipped scripts do exactly that — all 12 sites of the bomb sequence are
   `timer.mode 12` (countdown | visible), `timer.set 900`, **then op 112**.
   Under the table's names that reads "configure the timer, then stop it";
3. the shooting range does `shoot.end`, **op 111**, then `var.set.timer` into a
   `TEMPS n` variable it shows with `ui.highscore` — a stop followed by reading
   the time off the stopped clock.

Sites: 13 of 111, 15 of 112, 12 each of mode (always `12`) and set (always
`900`), 5 of 115, **0 of 110**.

`tables/vm_opcodes.json` is T8's file and was not edited here. The port's
methods are named for what they DO, so **T12 must wire op 111 → `timerStop`
and op 112 → `timerStart`**; `gamestate.h` says so at the declarations.

## 3. A second correction: issue 29 states op 49's operands backwards

Issue 29 says "49 scans list `field1` for object `field0`". The handler at
0x0040A440 does the reverse: the FIRST fetch indexes the list table
(`lea eax, [esi+esi*2]` → `word_69BD62[eax*4]`) and the SECOND is what is
announced to `OBJECTS` and compared against the entries. So **field 0 is the
list and field 1 is the object** — which is what `tools/script_dump.py`'s
`DOMAIN_FIELD` has had all along ("field 0 selects one of four object lists"),
and what ops 50 and 51 do too.

## 6. Doc text for `docs/GAME_STATE.md`

### 6a. Append to §3, "The object lists", after the four-row list table

> ### What the four opcodes do to a list
>
> The list is a plain array with a terminator and no stored count, so every
> operation has to leave that recoverable. All four are transcribed in
> `engine/src/script/gamestate.cpp`; `verify.py: engine game state` runs them.
>
> | op | function | what it does |
> |---|---|---|
> | 49 `var.set.has_object` | 0x0040A440 | scans the first `count` entries of the list in **field 0** for the object in **field 1**, and writes 1 or 0 into the variable in field 2 |
> | 50 `inventory.add` | 0x0040A4D0 → `Inventory_Insert` 0x004098E0 → `ObjectList_InsertFront` 0x00409CB0 | inserts at the **front**, refusing a full list |
> | 51 `inventory.remove` | 0x0040A5A0 | removes one copy, shifting the tail down and writing `0xFFFF` into the **last** slot |
> | 52 `inventory.remove_all` | 0x0040A6A0 | the same removal repeated until the id is gone |
>
> **The insert is at the FRONT, not the end.** `ObjectList_InsertFront` is
> `memmove(base + 2, base, 2 * capacity - 2)` and then `base[0] = id`, so the
> newest item is index 0 and the terminator slides up one slot; dropping the
> last slot is safe because the function's first line is
> `if (capacity == count) return 0`. An append is self-consistent — it keeps
> the terminator scan true and every count right — and it puts the wrong item
> under the inventory screen's cursor, which is the shape of error §1 warns
> about.
>
> **The duplicate refusal belongs to the list, not to the opcode.** The 50
> handler scans for the id first only when its list selector is 2 or 3
> (`cmp edi, 3 / cmp edi, 2`), so the memo journal and the shop stock cannot
> hold two of anything and the two carried lists can.
>
> Each list also has a **parallel 56-byte record array** (`dword_69BD68`,
> copied out of `IAM\OBJECT` on insert) that the removals shift in step. It is
> a runtime cache, not state: it is not in the DB, it is not saved, and a
> replica rebuilds what it holds from the object table by id.

### 6b. Append to §2's accessor table, under "prop state"

> **`ObjectState_Get` sign-extends, and the port reproduces it.** The byte is
> loaded `movsx`, the mask `3 << 2*(i % 4)` is built in a byte register and
> sign-extended as well (0xC0 at `i % 4 == 3`), and the result is `sar`'d — so
> for indices ≡ 3 (mod 4) state 3 reads back as **−1** and state 2 as **−2**.
> Nothing in the game can see it: op 68, op 76 and `Scene_LoadProps` all mask
> the low byte (`test al, 1`, `or al, 2`). It is recorded because a replica
> that "corrects" it and a replica that keeps it are indistinguishable until
> something compares the value rather than masking it.

### 6c. A new section, after §5 (the clock)

> ## The script timer
>
> Five opcodes and one read, over three globals — `g_TimerFlags`
> (`dword_930768`), `g_TimerValue` (`dword_930764`) and `g_TimerStart`
> (`dword_930760`). None of them is in the 8192-byte block and none is saved:
> the timer does not survive a reload, while the clock it counts against does
> (day and time travel in the save slot's own header, `GAME_STATE` 8).
>
> | op | address | jumps to | what it does |
> |---|---|---|---|
> | 110 | 0x00405340 | `sub_41E260` | `flags = 1` — a reset. Unnamed in the table, **0 shipped sites** |
> | 111 | 0x00405350 | `loc_41E2B0` | requires `!(flags & 1)`; `flags \|= 1` — **STOP** |
> | 112 | 0x00405360 | `loc_41E2D0` | requires `flags & 1`; `start = clock`; `flags &= ~0x11` — **START** |
> | 113 | 0x00405370 | `Timer_SetValue` 0x0041E270 | `value = field * 1000`, refused unless stopped |
> | 114 | 0x004053D0 | `Timer_SetMode` 0x0041E290 | `flags = field \| 1`, refused unless stopped |
> | 115 | 0x00405420 | `Timer_Elapsed` 0x0041E430 | `Var_Set(field, elapsed)` |
>
> **The names in `tables/vm_opcodes.json` for 111 and 112 are inverted.** The
> table calls 111 `timer.start` and 112 `timer.stop`; the two functions they
> jump to say the opposite, and neither carries a `proc` label — they are
> reached only by a tail `jmp`, so they are absent from the decompilation and
> have to be read at the addresses the handlers name. Three things settle the
> direction:
>
> * `Timer_SetValue` and `Timer_SetMode` both bail unless `flags & 1`, so the
>   configure pair can only precede the start;
> * every one of the 12 Tetra-bomb sites is `timer.mode 12`, `timer.set 900`,
>   **then op 112** — under the table's names, "configure the timer, then stop
>   it";
> * the shooting range does `shoot.end`, **op 111**, then `var.set.timer` into
>   a `TEMPS n` variable it shows with `ui.highscore` — stop, then read.
>
> Sites: 13 of 111, 15 of 112, 12 each of 113 and 114 (always `900` and `12`),
> 5 of 115, 0 of 110.
>
> **The flags**, from `Timer_Format` (0x0041E300) and the HUD tick
> (`sub_41E480`): bit 0 halted — `Timer_Elapsed` reads 0 when the flags are
> *exactly* 1; bit 2 count **down** (the display shows `value - elapsed`, and
> `Timer_Elapsed` does **not** apply it); bit 3 draw the `HH:MM:SS` readout;
> bit 4 expired — set when the clock passes `start + value`, which also raises
> event 43 with parameter 18 and freezes the reading at the value. Mode 12 is
> `countdown | visible`, and with the `| 1` the setter adds it is the only mode
> the shipped scripts ever ask for.
>
> **The unit is a millisecond**, which is the clock's (§5): `Clock_Tick` adds
> 166 units per 5 frame units — 996 a real second — `Timer_Format` divides by
> 1000 for seconds, and op 113 multiplies by 1000, so `timer.set 900` is
> fifteen minutes.

## 7. Where the engine did not settle it — every choice made here

1. **`listClear` has no engine counterpart.** Op 52 with id −1 is not a clear:
   it removes every entry whose 56-byte cache record has bit 1 of `+0x24` set,
   which needs the array the port does not keep. `listClear` writes the
   terminator into every slot — the state a fresh DB ships with — and its
   comment says it is port-side only.
2. **`propState` keeps the sign extension; `propStateBits` does not.** Both are
   provided because no shipped caller distinguishes them, so the corpus cannot
   choose. The exact transcription is the default.
3. **The clock and timer live on `GameState`** though they are exe globals, not
   DB fields. The alternative was a new type; this keeps the state a script
   touches in one place. They are excluded from `raw()`, `walk()`,
   `relocate()` and the save path, and the header says so.
4. **`timerSet` takes milliseconds**, and the ×1000 stays in the opcode where
   the handler does it. `Timer_SetValue` itself takes the raw value.
5. **Method names follow the mechanism, not the table** — `timerStop` is op
   111 and `timerStart` is op 112. Naming them after the table would have made
   `timerStart()` the one that halts.
6. **`timerCheckExpiry` is split out of `sub_41E480`.** That function also
   draws the readout and raises event 43; only the state half is here, and the
   caller raises the event.
7. **`Inventory_Insert`'s quantity merge is not modelled** (see §1). A script
   that gives the player a second clip of the same ammunition will take a list
   slot in the port where the engine bumps a quantity. This is the one known
   gap in the list layer, and it needs the 56-byte cache, i.e. the inventory
   channel, not the DB.
8. **`objectList()` in `inventory.cpp` disagrees with `listCount`** and was
   left alone (not this task's file): it collects every slot with `v > 0` over
   the whole capacity, where `ObjectList_SetCapacity` stops at the first
   terminator and would count a legitimate id 0. No shipped list has a hole or
   an id 0, so the two agree on all shipped data today. Worth unifying when
   somebody owns that file.
