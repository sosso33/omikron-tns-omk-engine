## 1. Issue 31 — opcodes 43 and 44 are 42's siblings

### 1a. The assembly

All three handlers open with the same 16-bit **target** fetch through the shared
form (`Runtime.exe.asm` 2800–2951; `clean/_vmhandlers.json` keys `402940`,
`4029A0`, `402A30`; `python3 tools/asmfn.py 402940` / `4029A0` / `402A30`):

```
mov     dl, [esi]                  ; ctx+0Ch is the pc
mov     ch, [esi+1]
or      edx, ecx
lea     ecx, [esi+2]               ; pc += 2
cmp     dx, 0FFFFh
mov     [eax+0Ch], ecx
jz      short loc_4029D1
test    dh, 40h                    ; the 0x4000 indirect
jz      short loc_4029D1
mov     esi, [eax+24h]             ; the context's variable table
and     dh, 0BFh
movsx   edx, word ptr [esi+edx*2+2]
```

and then peek the stack top — `[ctx+10h]` the stack base, `[ctx+14h]` the stack
pointer, `[base + sp*4 - 4]`, **nothing pops**:

```
op 42 (0x00402940)  mov edi, [eax+10h] / mov dx, [eax+14h] / mov edi, [edi+edx*4-4]
op 43 (0x004029A0)  mov esi, [eax+10h] / mov dx, [eax+14h] / mov ebp, [esi+edx*4-4]
op 44 (0x00402A30)  mov edx, [ecx+10h] / mov ax,  [ecx+14h] / mov edx, [edx+eax*4-4]
```

The three differ only in the **label** read after the target:

* **42, one byte** (`Runtime.exe.asm` 2830–2840):

  ```
  inc     ecx
  mov     dl, [ecx-1]
  mov     [eax+0Ch], ecx
  movsx   ecx, dl
  cmp     edi, ecx
  jz      short loc_402993        ; equal -> fall through
  mov     [eax+0Ch], esi          ; differ -> pc = target
  ```

* **43, two bytes, and they go through the SAME 0x4000 indirect as the target**
  (`Runtime.exe.asm` 2872–2894):

  ```
  add     ecx, 2
  mov     ebp, [esi+edx*4-4]
  xor     edx, edx
  mov     dl, [ecx-2]             ; <- the low label byte
  mov     [eax+0Ch], ecx
  mov     esi, edx
  xor     edx, edx
  mov     dh, [ecx-1]             ; <- the high label byte
  or      esi, edx
  cmp     si, 0FFFFh
  jz      short loc_402A13
  test    esi, 4000h
  jz      short loc_402A13
  mov     ecx, [eax+24h]
  and     esi, 0FFFFBFFFh
  movsx   esi, word ptr [ecx+esi*2+2]
  loc_402A13:
  movsx   edx, si
  cmp     ebp, edx
  jz      short loc_402A1D        ; equal -> fall through
  mov     [eax+0Ch], edi          ; differ -> pc = target
  ```

* **44, four bytes, a plain int32 with no indirect** (`Runtime.exe.asm`
  2928–2951):

  ```
  mov     eax, edi
  add     edi, 4                  ; <- the four label bytes
  mov     bl, [eax]
  inc     eax
  mov     esi, ebx
  xor     ebx, ebx
  mov     bh, [eax]
  mov     [ecx+0Ch], edi
  or      esi, ebx
  inc     eax
  xor     ebx, ebx
  mov     bl, [eax]
  shl     ebx, 10h
  or      esi, ebx
  xor     ebx, ebx
  mov     bl, [eax+1]
  shl     ebx, 18h
  or      ebx, esi
  cmp     edx, ebx
  jz      short loc_402AA4        ; equal -> fall through
  mov     [ecx+0Ch], ebp          ; differ -> pc = target
  ```

So the operand lengths are **2 + 1 = 3** (42, already in `LEN_FIX`),
**2 + 2 = 4** (43) and **2 + 4 = 6** (44), against the table's 0 for all three.
A decoder trusting the table desynchronises from the label byte on.

`dialog_disasm`'s listing rendered operands by `len(ops)`, which is exactly the
trap here: 43's four bytes would have printed as an int32 and 44's six as no
operand at all. The `case` family is now keyed on the **opcode**
(`CASE_LABEL`), and the shared-fetch rendering was factored out into
`word_operand(b)` so the target and 43's label use one implementation:

```

44 case.i32  target 16, case -1234
```

## 5. Ops 111 / 112 are named backwards (T6's finding) — CONFIRMED, but not by
the route I was given

**The conclusion is right and the names are swapped. Two of the three premises
in the message I received are wrong, and both would have flipped the answer, so
the derivation is rewritten here from the image.**

### 5a. Which handler jumps where — read from the executable's own bytes

The message says *"0x405350 (op 111) jumps to loc_41E2D0 …, 0x405360 (op 112)
jumps to loc_41E2B0"*. That is **transposed**. `Runtime.exe.asm` has these four
handlers as unlabelled 16-byte blocks separated by `align 10h`, which is easy
to miscount, so I decoded the bytes instead:

```
op 111  0x405350  a1 e0 05 6a 00 85 c0 75 05 e9 52 8f 01 00 c3 90
    mov eax, ds:0x006A05E0 / test eax,eax / jnz 0x40535E / jmp 0x0041E2B0
op 112  0x405360  a1 e0 05 6a 00 85 c0 75 05 e9 62 8f 01 00 c3 90
    mov eax, ds:0x006A05E0 / test eax,eax / jnz 0x40536E / jmp 0x0041E2D0
```

So **111 -> 0x0041E2B0** and **112 -> 0x0041E2D0**. (`tools/verify.py:3423`
already has this pairing the right way round — only the relayed message was
transposed.) For the record, 110 -> `sub_41E260` and 109 is a bare `retn`.

### 5b. What the two routines do (`Runtime.exe.asm` 45934–45961)

```
loc_41E2B0:                     ; op 111
mov     cl, byte ptr dword_930768
mov     eax, 1
test    al, cl
jz      short loc_41E2C2        ; bit 0 CLEAR -> proceed
xor     eax, eax
retn                            ; bit 0 already set -> refuse
loc_41E2C2:
or      dword_930768, eax       ; SET bit 0
retn

loc_41E2D0:                     ; op 112
mov     cl, byte ptr dword_930768
mov     eax, 1
test    al, cl
jnz     short loc_41E2E2        ; bit 0 SET -> proceed
xor     eax, eax
retn                            ; bit 0 clear -> refuse
loc_41E2E2:
mov     ecx, dword_4C2BD0
mov     dword_930760, ecx       ; start = the running clock
mov     ecx, dword_930768
and     ecx, 0FFFFFFEEh         ; clear bits 0 and 4 (bit 2, the mode, SURVIVES)
mov     dword_930768, ecx
retn
```

Taken alone this reads the wrong way — 111 *sets* a flag, 112 *clears* one —
and that is exactly the trap. The second wrong premise is the guard sense:
`Timer_SetValue` (`sub_41E270`, op 113) and `Timer_SetMode` (`sub_41E290`,
op 114) both `jnz` on bit 0, i.e. they **refuse unless bit 0 is SET**, not
"unless the timer is stopped".

### 5c. What settles it: the READER, `sub_41E300`, which nothing had cited

`sub_41E300(&h, &m, &s)` at `Runtime.exe.asm` 45966–46060 is what op 115
`var.set.timer` reports, and it names every field:

```
mov     eax, dword_930768
test    al, 10h
jz      short loc_41E378
    ... report dword_930764 flat              ; bit 4 = FROZEN
loc_41E378:
cmp     eax, 1
jnz     short loc_41E39F
    ... report 0 / 0 / 0                      ; the word EXACTLY 1 -> ZERO
loc_41E39F:
mov     ecx, dword_4C2BD0
mov     esi, dword_930760
sub     ecx, esi                              ; elapsed = NOW - START STAMP
test    al, 4
jz      short loc_41E3BB
mov     edx, dword_930764
sub     edx, ecx                              ; bit 2 -> remaining (countdown)
mov     ecx, edx
loc_41E3BB:
    ... /1000, /60, /60 into s, m, h
```

So `dword_4C2BD0` is the **running clock**, `dword_930760` the **start
stamp**, `dword_930764` the duration in ms (op 113 stores `field0 * 1000` —
its operand is seconds), bit 2 the countdown mode, bit 4 a freeze — and
**bit 0 is not "running", it is "being CONFIGURED"**. A timer whose word is
exactly 1 reads 0/0/0; a timer runs when bit 0 is CLEAR and a stamp has been
written.

That inverts the surface reading and gives the sequence:

1. **111** claims the timer (`or bit 0`, refusing if already claimed) and it
   now reads **0/0/0** — the **STOP**;
2. **114 / 113** configure mode and duration, both legal only while bit 0 is
   set, i.e. only between a stop and a start;
3. **112** writes `dword_930760 = dword_4C2BD0` — **stamping NOW as the start**
   — and clears bit 0 and the freeze while keeping the mode bit: the **START**.

### 5d. The corpus is exactly that shape

Every occurrence of ops 109–115 in `IAM\AREA`+`SCENE`+`GLOBAL`+`DIALOG`, in
script order:

```

sequences within one script      adjacent pairs
  114 -> 113 -> 112   x12          114 -> 113  x13
  111                 x8           113 -> 112  x12
  111 -> 115          x5           111 -> 115  x5
  112                 x3           110 -> 114  x1

```

`mode, set, 112` twelve times — the Tetra bombs, 900 s and mode 12 at all
twelve — is a **start**, and `111` alone or `111 -> var.set.timer` is a stop
followed by a read of the zero. Neither ordering makes sense under the old
names: 113/114 would be configuring a timer they then *stop*, and the stop
clears bit 0 so a following configure would refuse.

Names swapped: **111 = `timer.stop`, 112 = `timer.start`**.

`corrected` is unchanged for both (they take no operands and the table's 0 is
right); the `named` total does not move either, since this is a swap.
