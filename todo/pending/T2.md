## Doc text

**docs/SCRIPT_VM.md** (the status/resume map, beside T10's):

> `dialog.start` (61) is the one opcode where `Script_Execute` RETURNS —
> `if (v4 == 61) return;` — and it returns for that context alone; the pump's
> slot loop continues and `Game_Tick` still ticks the camera. What stops the
> world during a conversation is `Script_ProcessActions`' `g_DialogState == 3`
> gate on the NEXT frame, not the return. A screen closed without a choice
> resumes its script too: `UI_OpenScreen` seeds the answer at -1, every close
> path posts event 5 with it, and case 5 does `Var_Set(var, -1)` and status 1.
> `Message_RunHandlers` (0x00409420) gives a handler a fresh context whose
> parameter block is `{message, sender}`; the shared fetch reads the block from
> its SECOND word, so `push.i16 0x4000` — all 22 shipped uses — pushes the
> sender. Message 25 runs inline; every other one is queued (actions 1, 4).
> `scene.load` / `scene.unload` (71/72) on an area in a resident slot swap the
> scene in the same frame: the old SCENE block's context is freed, the new
> block's `+4` script is queued. `Area_LoadIntoSlot` (0x00402B70) into a slot
> that already holds the area only refreshes the fog and returns, so an
> A -> B -> A return runs no startup script.

**docs/GAME_STATE.md** (the player record):

> `player.become` (56, handler 0x402F60) is what fills the player record at
> +60: `strcpy` of the actor record's two bio pointers into +336 and +592, then
> `rep movsd` of 0x43 dwords from the record's +8 into +68 — everything but
> the two pointers `State_Apply` plants. So the record's +272 is the player's
> actor id, `IAM\START` ships it as -1, and AREA 118's startup script writes
> 136 (`KUM_FN`) before anything else. `character.show`/`hide` (78/79) write
> the character record's +18 into the +20 bitmap (`ObjectShown`); `hide -1`
> is the player and writes no bit.

**engine/README.md** (the audit table): the actor-runtime and game-state rows
gain "player.become into the DB record and bios", "message dispatch
(`Session::postMessage`)", "scene.load/unload on the resident area", "the
resident-return skip", "the ObjectShown bit". `Actors_SpawnFromTables`
reading that bit back on load is NOT ported (below).

## Not done, and why

* **`Actors_SpawnFromTables`** — the bit's consumer — is not ported: on a
  fresh area load the Session's `shown_` is not rebuilt from the bitmap
  (START has 628 of 1032 bits set, none of AREA 118's two). Doing it would
  change what `omk-play` draws on every transition and belongs with the
  transition machine (T11), not with a bit write.
* The sender's slot -> id mapping (`Actor_IdBySlot` for messages 0..12 but 4,
  `ObjectSlot_Id` for 4/20/25): no slot tables in the Session; passed through.
* `Zones_RegisterAll` after 71/72: no zone model in the Session (issue 10).
* A `scene.load`/`unload` aimed at the OTHER resident slot's area would swap
  that slot's scene in the engine; the Session holds only its id (issue 15).
* On a resident return the returning area's `.SCX` is loaded FRESH (labelled
  in `finishAreaTransition`): the engine still holds it with its programs.
* Message 0 sets `byte_4C012C` (the "message-0 handler running" marker `end`
  clears, issue 38): not modelled.
* `dbWrite` is the const_cast stand-in for a `GameState` byte writer (above).
