## 1. What changed, and the engine line each transcribes

The port had a zone runtime and it was only ever a HARNESS. `World`
(`world.cpp`) takes one chunk of one kind and runs the scripts itself; the
thing `omk` and `omk-play` actually run — `Session` — had no zone model at
all, so in the live replica **no zone ever armed** and every conversation had
to come out of a startup script. That is issue 10, and it is what
`ZoneRegistry` closes.

It is deliberately **not a second scheduler**. `world.h`'s `Zone`, `zonesOf`,
`contains`, `centre` and the `kZoneUnit` quad conversion are reused verbatim,
and nothing here runs a script: every action the pump would queue comes back as
a `ZoneEvent` carrying the zone id, the action number, the script offset and
the chunk it is relative to. The activate DEDUPE stays where the engine keeps
it — in the context's own 4-deep FIFO and its `+32` — which is the Session's,
not the zone's.

### `Zones_RegisterAll` (0x00406560) — the four tables and both slots

```
Zones_Clear();
for (blocks = dword_69BC40; blocks < &dword_69BC60; blocks += 4, ++areaSlot) {
    if (blocks[2] != -1 && blocks[0])          // the AREA's table
        for (rec = u32(blocks[0], 48), n = i16(blocks[0], 76); n--; rec += 68)
            if (Zone_StateBit(u16(rec + 12, 52))) Zone_Add(rec + 12, areaSlot);
    if (blocks[3] != -1 && blocks[1])          // the SCENE loaded OVER it
        for (rec = u32(blocks[1], 16), n = i16(blocks[1], 44); n--; rec += 68)
            if (Zone_StateBit(u16(rec + 12, 52))) Zone_Add(rec + 12, areaSlot);
}
```

Two slots × two tables = four walks, and the guard is the id **and** the block.
`ResidentSlot` is that 16-byte record (`dword_69BC40/44/48/4C`) with the chunks
as spans; `registerAll` is the loop, gated on `StateArray::ZoneState` —
**confirmed as array 5** from `Zone_StateBit` (0x0040D500), which indexes
`u32(g_GameDB, 28)`, and `gamestate.h` already names `+28` array 5.

`Zone_StateBit` masks the id to 15 bits, so bit 15 — the one-shot flag — is
stripped for registration and read back whole by the pump. `Zone::stateBit()`
and `Zone::oneShot()` are `world.h`'s and are used as they stand.

### The prune — `Zones_RegisterAll`'s tail

```
for (ctx : the 32 context slots)
    if (ctx && u16(ctx, 42) != -1 && !Zone_FindScriptsById(u16(ctx, 42))) {
        for (ps : the 16 prompt slots)
            if (u32(ps,0) == ctx) { u32(ps,0)=0; ps[5]=-1; ps[4]=0; --dword_4E6B24; }
        Mem_Free(...); dword_4E61E8[u8(ctx,30)] = 0;
    }
```

Split in two because the contexts belong to the Session: `registerAll` does the
**prompt-slot** half itself (a slot whose zone no longer resolves is released
and reported by `detached()`), and `prune(contextZones)` returns the ids whose
contexts the caller must free.

`Zone_FindScriptsById` (0x00406760) searches the resident chunks' **full**
record tables, not the registered subset — so a zone whose save bit a script
has just cleared with `zone.disable` still resolves and its context survives.
Only unloading its area prunes it. `resolve()` reproduces that, over `all()`,
in the engine's own order (slot 0 AREA, slot 0 SCENE, slot 1 AREA, slot 1
SCENE).

### `Actor_ScanZones` (0x00467770) — and the arc is **not** what the file holds

Containment first, event 8 for every zone the point is inside, then the arc and
event 7. `Zone_ContainsPoint` (0x0048C880) is a crossing count over the four
corners and **ignores y** — the third argument is passed and never read, which
is why `Zone::contains(x, z)` is the right call.

The facing test is where a new fact came out of the loaders. `Area_Load`
(`01_file.c`, the per-zone relocation loop) converts the arc **in place**:

```
u16(rec, 62) = (int)((double)u16(rec, 62) * 0.087890625);   // 360/4096
u16(rec, 60) = (int)((double)u16(rec, 60) * 0.087890625);
```

so `Actor_ScanZones` compares whole **degrees** against the actor's facing
(`f32(actor, 420)`, a float in degrees) while the field on disk is a
4096-per-turn angle — the unit `docs/FILE_FORMATS.md` §5b2b records and
`verify.py: zone records` asserts ("0 arcs past 4096"). Both readings are
right; they are one conversion apart, and nothing had crossed it because
`World` never had an actor with a real yaw in the same frame.

`zoneFacesDegrees` is the engine's test at the engine's unit, wrap arms
included:

```
if (u16(zone,50)) {                      // a zero WIDTH accepts any facing
    lo = mid - (wide >> 1); hi = mid + (wide >> 1);
    if (lo >= 0) { if (hi > 360 && facing < lo) facing += 360; }
    else if (!(facing < lo + 360 && facing <= hi)) { lo += 360; hi += 360; }
    if (!(facing >= lo && facing <= hi)) continue;
}
```

`Zone::faces` (world.h) is the same arc measured in the stored 4096 unit and
rounded differently; it is left alone for `World`, and the live scan uses this
one. The one line here that is **not** in the assembly is the `fmod` that wraps
the incoming facing into [0, 360) — labelled in the source, and a no-op for a
facing already in range.

### The 16 prompt slots — `Script_Pump` (0x00407DC0) and `Game_HandleEvent`
### case 7 (0x004067D0)

Modelled **as the state machine**, with the engine's own words, which is the
one thing T4 explicitly left implicit ("`World` derives *armed* from the
position and facing each step instead of keeping the 16 prompt slots"). The
slot is 16 bytes: `+0` context, `+4` the zone record, `+8` state, `+10` the
zone id, `+12` the area slot.

| state | name | who writes it | to what |
|---|---|---|---|
| 0 | empty | pump case 3/5, the prune | — |
| 1 | new | case 7, taking a free slot | pump case 1 → 3 |
| 2 | pressed | case 7, from 3 | pump case 2 → 3, or 5 if one-shot |
| 3 | armed | pump cases 1 and 2 | case 7 → 2; a pump that still finds 3 → leave |
| 4 | latched (scanned) | case 7, from 5 | pump case 4 → 5 |
| 5 | latched / leaving | pump case 2 (one-shot) and case 4 | case 7 → 4; a pump that still finds 5 → leave |

The ORDER is what makes this work and it is measured, not assumed:
`Script_Pump(1)` is `readable/src/05_sys.c:2107` and `Actors_TickAll()` is
`:2178`, both inside `Game_Tick`, with **no dialogue gate on the actor tick**.
So the pump always reads the states the *previous* frame's scan left, and 4/5
ping-pong for as long as the player stands in a one-shot zone — T4's correction
to issue 5, re-derived here from the same two functions and now expressed as
the states rather than as a `spent` flag.

That is why `pumpSlots` and `scanZones` are separate public calls: the Session
runs the first at the top of its frame and the second at the bottom, exactly
where `Game_Tick` runs them. `scan()` does both in that order for a probe.

Three details that are the engine's and would not be guessed:

* **the enter script is conditional, the leave is not.** Case 1 is
  `if (zoneScripts[0]) Script_QueueAction(ctx, 1);` with *both* arms writing
  state 3, so a zone with no enter script still holds its slot; cases 3/5 queue
  actions 3 and 4 unconditionally, and `Script_ProcessActions` consumes an
  action whose script slot is 0 and leaves the context idle. `world.cpp` guards
  both; this guards only the one the engine guards. (AREA 76 zone 1466 has no
  enter script and is the shipped case — its `Arm` event carries action 0.)
* **no activate script, no latch.** Case 2 tests `u32(ctx, 4)` before anything
  else, so a one-shot zone with an empty activate slot is spent by nothing.
* **the press is gated on the prompt table.** `Game_HandleEvent` case 6 is
  `if (g_DialogState == 3 || a2 != 4 || !dword_4E6B24) return 0;` — a press
  with no slot armed never becomes `dword_4E6C90` at all, so `pumpSlots` gates
  it on `armedCount()` rather than trusting its caller.

### What is NOT modelled, and is labelled in the source

* **the case-2 inline dry run.** The engine runs the context's current script
  as a dry run before queueing — `Script_Run`, or `Script_RunToOpcode75` while
  the player holds an object — and its return decides only whether the press
  counts as *consumed* (`dword_4E66B8`, issue 7), never whether the activate is
  queued: empty-handed both outcomes fall into `loc_407F93`. So with empty
  hands the queue is unconditional and this reproduces it exactly.
  `setHeldObject(true)` makes the registry *refuse* the queue rather than
  guess, because `Script_RunToOpcode75`'s answer is not modelled anywhere in
  the port.
* **seventeen simultaneous zones.** Case 7's free-slot search leaves `v26 = 0`
  and then writes `v26[5] = v24` **through it** — a null store, so the shipped
  game crashes on the 17th. Dropped and labelled; it is a bug, not a behaviour.
* **the context reuse arm** of case 1 (a zone re-armed while its free was still
  queued) is Session-side, because it manipulates the FIFO. Written out in §3.

### 3b. `area.cpp`

```cpp
void Session::registerZones() {
    std::vector<ResidentSlot> slots;
    for (int k = 0; k < 2; ++k) {
        ResidentSlot s;
        s.areaId  = slotAreaId_[k];
        s.sceneId = slotSceneId_[k];
        s.area    = {slotArea_[k].data(),  slotArea_[k].size()};
        s.scene   = {slotScene_[k].data(), slotScene_[k].size()};
        slots.push_back(s);
    }
    zones_.registerAll(slots, state_);

    // Zones_RegisterAll's tail: a context whose zone no longer resolves goes
    // with its area. `registerAll` has already released the prompt slots.
    std::vector<std::int16_t> ids;
    for (const auto& c : ctxs_)
        if (!c->done && c->zone != -1) ids.push_back(c->zone);
    for (const auto dead : zones_.prune(ids))
        for (auto& c : ctxs_)
            if (c->zone == dead) c->done = true;
}

Session::Ctx* Session::zoneContext(std::int16_t zone) {
    for (auto& c : ctxs_)
        if (!c->done && c->zone == zone) return c.get();
    return nullptr;
}

// Script_QueueAction (0x004063D0). The two refusals are one rule twice: a
// second ACTIVATE while one is queued or is the one being run. A FULL queue
// stores nothing and still returns 1.
int Session::queueAction(Ctx& c, int act) {
    if (c.queue.size() >= 4) return 1;
    if (act == 2) {
        for (const int q : c.queue) if (q == 2) return 0;
        if (c.act == 2) return 0;
    }
    c.queue.push_back(act);
    return 1;
}

void Session::applyZoneEvents(const std::vector<ZoneEvent>& ev) {
    for (const auto& e : ev) {
        if (e.kind == ZoneEvent::Kind::Touch) continue;   // the scan's half
        Ctx* c = zoneContext(e.zone);
        if (!c) {
            // Only an Arm creates one - Script_Pump case 1's
            // `Script_NewContext(areaSlot, s[0], s[1], s[2])`.
            if (e.kind != ZoneEvent::Kind::Arm) continue;
            auto n = std::make_unique<Ctx>(state_, table_);
            n->code.assign(e.code.begin(), e.code.end());
            n->zone = e.zone;
            for (int k = 0; k < 3; ++k) n->slots[k] = e.scripts[k];
            n->chunkArea = curArea_;
            n->vm.setCameraWaitSuspends(camWait_);
            n->vm.setObjectWaitSuspends(objWait_);
            ctxs_.push_back(std::move(n));
            c = ctxs_.back().get();
        } else if (e.kind == ZoneEvent::Kind::Arm) {
            // Case 1's reuse arm: the zone re-armed while its FREE was still
            // at the head of the FIFO -
            //     if (ctx && u16(ctx,42) == slot.zoneId && u8(ctx,24) == 4)
            //         { u8(ctx,24) = 0; --u16(ctx,28); }
            // - cancel the free and keep the context, its stack included.
            if (!c->queue.empty() && c->queue.front() == 4) c->queue.pop_front();
        }
        if (e.action) queueAction(*c, e.action);
    }
}

// Script_ProcessActions (0x00408220), the zone half: dequeue ONE action, point
// the context at the matching script slot, set the status word. It does not
// execute - keeping the two apart is what makes a park possible.
void Session::processActions(std::size_t i) {
    Ctx* c = ctxs_[i].get();
    if (c->zone == -1 || c->done) return;         // a startup/message context
    if (dialogState_ == 3) return;                // `if (g_DialogState == 3) return`
    if (c->running || c->queue.empty()) return;
    c->act = c->queue.front();
    c->queue.pop_front();
    if (c->act == 4) { c->done = true; return; }  // action 4 frees it
    const int slot = c->act - 1;
    const auto off = (slot >= 0 && slot < 3) ? c->slots[slot] : 0;
    // `case n: ctx->pc = slots[n-1]; if (slots[n-1]) status = 1;` - an action
    // whose slot is 0 is consumed and leaves the context idle.
    if (off > 0) {
        c->pc = static_cast<std::size_t>(off);
        c->started = false;
        c->running = true;
    }
}
```

## 5. Doc text

### For `docs/SCRIPT_VM.md`, with the zone lifecycle (T10/T14 own the file)

> ### The 16 prompt slots, as a state machine
>
> `Script_Pump` (0x00407DC0) and `Game_HandleEvent` case 7 (0x004067D0) share a
> 16-entry table (`unk_4E6B30`, 16 bytes: `+0` context, `+4` the zone record,
> `+8` state, `+10` the zone id, `+12` the area slot). The pump reads it, the
> actor scan writes it, and **the pump runs first**: `Script_Pump(1)` is
> `Game_Tick`'s :2107 and `Actors_TickAll` its :2178, with no dialogue gate on
> the actor tick.
>
> | state | set by | what the pump does with it |
> |---|---|---|
> | 0 | the release, and the prune | nothing - the id at `+10` is -1 |
> | 1 | case 7, taking a free slot | make the context, queue action 1 if the zone has an enter script, → 3 |
> | 2 | case 7, from 3 | with the press: queue action 2, then → 5 if the zone id's bit 15 is set, else → 3. Without: → 3 |
> | 3 | the pump, from 1 and 2 | still 3 means nothing re-armed it - queue actions 3 and 4, release the slot |
> | 4 | case 7, from 5 | → 5 |
> | 5 | the pump, from 2 (one-shot) and 4 | as 3 |
>
> So an armed zone ping-pongs 3 → 2 → 3 for as long as the player faces into
> it, and a **one-shot** zone ping-pongs 5 → 4 → 5 instead: the bit does not
> free the zone, it latches the slot out of the press cycle, and the leave
> happens on leaving like any other zone. Three of the transitions are
> conditional and the conditions are not symmetric: the *enter* script is
> queued only if the zone has one (both arms still write 3), the *leave* and
> the *free* are queued unconditionally, and the press does nothing at all
> unless the zone has an **activate** script - which is also why a one-shot
> zone with no activate script is never spent.
>
> An action press with no slot armed never reaches the pump: `Game_HandleEvent`
> case 6 is `if (g_DialogState == 3 || a2 != 4 || !dword_4E6B24) return 0;`.
>
> ### The arc is converted at load
>
> `Actor_ScanZones` compares the actor's facing (`f32(actor, 420)`, degrees)
> against `u16(zone, 48)` / `u16(zone, 50)` — the record's `+60`/`+62` **after**
> `Area_Load` has multiplied both by `0.087890625` = 360/4096. The field on disk
> is a 4096-per-turn angle (FILE_FORMATS §5b2b); the runtime one is whole
> degrees. A zero width — authored, or small enough to truncate to zero —
> accepts any facing.

### For `docs/FILE_FORMATS.md` §5b2b, one line beside `+60`/`+62`

> …4096-step angles **on disk**: `Area_Load`/`Scene_Load` convert both in place
> by 360/4096 as they relocate the record, so every runtime consumer
> (`Actor_ScanZones`) reads whole degrees.

## 7. What I could not establish

* **`verify.py` was not run** (task rule), so the check is written and its
  parser exercised standalone, not as a `verify.py` check.
* **The Session wiring is TEXT, not code.** `area.{h,cpp}` is T11's this batch,
  and T11 is rewriting the transition machine that owns the two resident slots
  — so `registerZones()`'s `slotArea_`/`slotAreaId_` arrays are written against
  a slot model that does not exist yet (issue 15). Filling slot 0 alone is
  correct and gives the registry `World`'s reach plus the SCENE table; the
  second slot needs T11's.
* **`prune` is exercised only by unloading everything.** The interesting case —
  slot 1 replaced while slot 0 stays — needs the two-slot transition, so
  scenario 5 registers AREA 118 alone. The mechanism is the same either way
  (`resolve` over the surviving records), but the shipped A → B → A path has
  not been walked through it.
* **The inline dry run of pump case 2 is unported**, as it was in `World`. It
  decides `dword_4E66B8`, which is issue 7 (the unconsumed press → message 26),
  and with empty hands it cannot change whether the activate is queued. With a
  HELD object it can, and `setHeldObject(true)` refuses rather than guessing —
  so a use-object press through the registry is currently a no-op, and that is
  a labelled gap rather than a modelled behaviour.
* **The scan does not run during a conversation.** `Actor_ScanZones` is in the
  actor tick and has no dialogue gate, so the engine keeps raising touches and
  filling prompt slots while `Dialog_TickUI` owns the frame; `Session::frame`
  returns before the scan. The only case that can tell the two apart is a
  player who walks through a zone and out again mid-conversation, which is the
  same limit `world.cpp` labels.
* **`Zone::contains` casts its ray along the other axis** from
  `Zone_ContainsPoint` (0x0048C880), which crosses on X. Both are valid
  crossing counts over the same quad and they can only disagree exactly on an
  edge. Reused rather than re-transcribed, because it is `world.h`'s and the
  task says so — but it is a difference, and it is the one place a
  pixel-exact containment claim would need re-deriving.
* **No golden trace can adjudicate any of this.** `Zones_RegisterAll`,
  `Script_Pump` and `Actor_ScanZones` announce nothing to `Dbg_LogTagged`; only
  the opcodes an armed script goes on to execute do. The standard here is
  DATA-CONSTRAINED plus assembly-transcribed, not engine-verified — which is
  worth stating because `traces/impasse-walk.log` DOES contain the far side of
  it (the zones AREA 222 fires as the player walks the Impasse), so a
  Session-side replay once the wiring lands would be the first real oracle.
