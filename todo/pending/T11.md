## Findings on the way (corrections to what batch 1 / T10 wrote)

1. **The load does NOT take "at least nine pump frames".** Cases 2–8 are
   gated on `sub_41EFA0`, which is the async file reader's "queued read
   served" test (`Offset == 0 && served == queued`), and only the `.3DO` SET is
   read through it — `Area_LoadIntoSlot` sets mode 1 before `Area_Load`, and
   case 2 sets mode 0 right after the set, so the `.SCX`, map, actors, props,
   `.ani` and slider track are read synchronously and cases 2..9 all run in
   the one `Area_TickLoad` call that finds the set served. The set streams at
   `ElementSize = 0x20000` bytes per `sub_41F320` call, which sits at the end
   of the frame function after `I2D_Flush`. So a transition takes
   **ceil(set bytes / 131072)** frames: Anekbah 2099056 → 17, AImpasse 33392 →
   1, jaunpur 2103652 → 17. `Music_SetFadeMode` is misnamed: it is
   `Async_SetMode` (its only effect is `dword_4E91C0` and `ElementSize`; the
   name came from `Game_HandleEvent` case 9 wrapping `Music_PlayTrack` in
   mode 2 / mode 0, which is the music STREAM's slice). Worth a rename in
   `readable/` (not my file). The boot load is mode 0 and takes 0 frames,
   which is what the port always did.
2. **The active row is switched by event 9, not by the transition.**
   `Area_TickLoad` case 9 sets `dword_69BC60`/`dword_69BC64` only for the
   duration of the two `Script_NewContext` calls and restores them. The switch
   is `Game_HandleEvent` case 9 — raised by `Walk_ProbeGround` (0x00467030)
   and `sub_459AA0` when the decor under the actor changes to a slot in state
   2 — which toggles the row, re-registers the zones and plays the area's own
   music (`AREA +142`). The transition machine only shows (`sub_419AF0`) and
   hides (`sub_419A90`) decors. Ported as `playerOnArea(area)`; the walker
   (E2) should call it when the ground decor changes; until then
   `placeActorAt` raises it for a teleport into the other slot's area, and
   the completion arms raise it for the destination when nothing has
   (RECONSTRUCTION, labelled in `areaTransition`'s `hideOutgoing`).
3. **441 of the 448 object-carrying `area.goto` sites are zone ENTER scripts**
   (record field 0), 7 activate, 1 in SCENE — not activate scripts. The
   objects are door pairs: AREA 0 zone 3 is `area.goto 201, 153, 240` and
   153/240 are `ported43open`/`ported43close` (linked, on set piece
   `Ported43`). So a door zone is: walk in → the destination streams → the
   door opens (on the outgoing scene) → the leave when the player's feet cross
   the quad → the door closes → the caller resumes. 409 of 448 pairs resolve
   in the source `.SCX` by object id (the earlier 416 counted differently).
4. **`area.goto X -1 -1` at state 8 is a no-op that returns 1** (mode 0 case 8
   with `a6 == -1` → `LABEL_17`): a script that transitions twice without an
   `area.arrive` between does nothing the second time. `requestArea` (the
   probe entry) therefore issues the `area.arrive` for the caller-less
   request before a second request.
5. **The intro's `AREAS 222` is op 47 and its `AREAS 118` is op 48** —
   `traces/intro.log` shows the pushes from `0x4c0790` and `0x4c0798`; AREA
   118's `+4` script tail is `area.goto 222 -1 -1 / scene.load 222,55 /
   actor.goto_address 654 / area.arrive 118 / end`. The `engine: intro`
   docstring's "`area.goto 222` stages a load, the caller runs on to its
   `scene.load`" is now literally what happens, one slice later.
6. `Zones_RegisterAll`'s prune only touches contexts with a zone id
   (`+42 != -1`); an area's STARTUP context that has ended stays in its table
   entry, at status 0, until its slot is evicted or `scene.load`/`unload`
   frees the SCENE's. So table entries are consumed by startup scripts across
   the whole play, which matters for the 32-entry cap.
7. SCENE 55's startup runs `player.become 49` at pc 1225 (the Impasse's
   Kay'l), which is why a restart probe reads the player as 49 before the
   restart and 136 after (AREA 118's `player.become 136` runs again in the
   restart frame).

## How the park is done without an interpreter change

`Script_Execute` needs the opcode BEFORE dispatch (the 45/47 refusal) and the
status word AFTER it (the transition's 9/10, the preload's 8). The
interpreter runs a whole script per call, so `Session::execute` hands it a
span that ends at the current instruction's last operand byte: it executes
that one instruction, fails the next fetch with `PcOutOfRange` and reports the
pc it reached (a jump target included; `steps >= 2` separates "executed one"
from "the chunk ends inside the instruction"). One `resume` call per
instruction; the scripts are tens of instructions a frame and the probe runs
in 0.4 s. No change to `interp.*` was needed, so nothing was delivered for T12.
If a `RunStatus::AreaOp` is ever wanted it would remove the per-instruction
call, nothing else.

## What is RECONSTRUCTION, labelled in the source

* The leave on a transition caller without a zone scan: issued the frame the
  departure object ends (`areaTransition` mode 4 case 5; `queueLeave`
  comment). Off with `setLeaveFromZones(true)`.
* Event 9 with no walker: `placeActorAt` raises it for a teleport into the
  other slot's area; the completion arms raise it for the destination when it
  is still the other row (`hideOutgoing`).
* A transition object that is not resident (or no scene loaded) "ends" the
  next frame (`startTransitionObject`, program -2) — the engine would wait on
  it until the 60 s watchdog; the same policy `ObjectWait` already takes.
* One `SceneRunner`: the departure/arrival objects run on the outgoing scene
  (kept until the transition completes), then the destination's `.SCX` is
  loaded fresh; the engine holds both scenes. The viewer draws ONE set
  (`setName()` = the shown slot), so during the door beats the destination
  set is drawn and the outgoing one is not, where the engine has both linked.
* The slice count is a data-constrained model of I/O pacing (the file size
  over `ElementSize`); the engine's count depends on nothing else, but no
  capture times a load, so it is tier 6 with a tier-2 input.
* `requestArea`'s implicit `area.arrive` for a second caller-less request.
* The watchdog is 1800 frames (60 s at 30 fps) rather than wall-clock.
* `hideSet` on the shown slot swaps the drawn set to the other slot (one
  drawable set), and `showSet` is only the slot switch; the fog block
  (`sub_41D380`) and `sub_41D4D0`/`sub_41D3F0` at case 9 are not modelled.
