## 1. What landed, file by file

### `src/formats/placements.{h,cpp}` — new, the 20-byte record

`struct Placement { int slot, actor; float pos[3]; float facing; int bit; }`
and `readPlacements(chunk, ChunkKind)`, written in the shape of
`formats/addresses.*` (same header-comment-carries-the-evidence style, same
`u32at`/`i16at` locals, same "an empty result is not an error").

Transcribes the record `Actors_SpawnFromTables` (0x0040BB90,
`readable/src/01_file.c:4815`, NAMED) consumes, from its own banner and its
body: `+0` the runtime slot written back, `+2` the actor id, `+4/+8/+12` the
coordinates, `+16` the facing, `+18` the `ObjectShown` bit. Tables at
**AREA +40 / count +72** and **SCENE +8 / count +40**
(`docs/FILE_FORMATS.md`, "the object table").

**Correction to the issue text, found by reading `Area_Load`.** The brief and
issue 40 quote the Demon's placement as `7605 -80 2980` facing `358`, which is
the arithmetic rounded. The engine **truncates all four**. `Area_Load`
(0x0040CC90, `01_file.c:5648-5661`) converts the object table **in place**
before anything reads it:

```
v28 = u32(v2, 40) + 8;                       /* record + 8 */
u32(v28 - 4, 0) = (int64_t)((double)(100 * u32(v28 - 4, 0)) * 0.00390625 * 0.3937007874015748 - 1.0);   /* x  */
u32(v28,     0) = ... ;                                                                                  /* y  */
u32(v28 + 4, 0) = ... ;                                                                                  /* z  */
u16(v28 + 8, 0) = (int64_t)((double)v34 * 0.087890625);                                                  /* facing */
```

and `Actors_SpawnFromTables` then reads the results straight back as floats
(`v20 = (float)i32(i, 4)` … `v23 = (float)i16(i, 16)`), which
`Actor_SetPlacement` (0x0041BDF0, `04_sys.c:6270`) stores unmodified at
`[58..60]`/`[61..63]` and `[105]`. So the engine's own numbers for actor 57
are **`7604 -79 2980` facing `357`** from the shipped `49457 -511 19386 4073`.
`rawToWorld` already truncates (its comment says why); the facing is truncated
here for the same reason.

The facing is **not** wrapped to (-180, 180] the way `angle4096` wraps a
camera's roll. Nothing interpolates two placements, which is the case
CLAUDE.md §1's wrapping rule exists for, and 357 is what the engine stores.

`Session::shownBitOf` now **uses this reader** instead of its own inline scan
of the same two tables — one reader, and the same answers (`session_probe`'s
`shown_bit actor 310 index 468 value 1` is byte-for-byte unchanged).

### `src/script/area.h`

* `Session::Character` — `{actor, slot, model, bank, pos[3], facing, bit,
  attached, fromScene}` — and `ResidentSlot::characters`, a
  `std::vector<Character>` in table order (the AREA's records, then the
  SCENE's). `model` is the actor record's `+144`, `bank` its `+72`.
* `Shown` keeps `actor` and `model` (play.cpp reads them) and gains `bank`,
  `pos[3]`, `facing`, `slot`, `fromTable`, so T20 can stage a body from the
  same struct.
* `bankOfActor(int)` beside `modelOfActor`, and `characterOf(int)` → the
  spawned record or `nullptr`.
* private: `actorSlots_` (100 `int16`, `word_69BC80`), `scriptShown_`,
  `spawnFromTables(slot, area, scene)`, `freeActorSlots(slot, area, scene)`,

### `src/script/area.cpp`

* **`spawnFromTables`** — `Actors_SpawnFromTables`, transcribed. Per record:
  the **first free** entry of the 100-entry table takes the **actor id**
  (`word_69BC80[v5] = v4` — the engine stores the id, not a busy marker; -1
  when full), its index is written back into the chunk at record `+0`; the
  actor record gives `+144` and `+72`; `attached` is the DB `+20` bit at `+18`
  **at the load**; and `Actor_FindById(id) + 270 = -1`, the held-object field,
  through the existing `findActorRecord`/`setHeldObjectOf`.
* **called in `completeLoad` BEFORE `loadProps`** — the engine's `Area_TickLoad`
  case 5 (`01_file.c:5371`, `Actors_SpawnFromTables(v3, v23, 1)`) precedes case
  6's `Scene_LoadProps`. The **boot** load reaches it: `loadArea` →
  `areaLoad` → `tickLoad` with `asyncMode_ = 0` → `completeLoad`, so no extra
  call was needed and none was added.
* **also called from `sceneLoad`**, which is a second engine call site the
  issue does not mention. Opcode 71's handler (0x403950) is
  `push 0 ; push esi ; push edi ; call sub_40BB90` — `a3 = 0`, the
  `if (!a3) goto LABEL_16` that skips the AREA half — immediately before
  `sub_409FC0` (`Scene_LoadProps`), which the port already modelled. Read with
  `python3 tools/asmfn.py --op 71`. Without this the Impasse's cast never
  appears, because the intro reaches 222 by `area.goto 222` and *then*
  `scene.load 222, 55`.
* **`freeActorSlots`** — `sub_40BEC0` (0x0040BEC0, the function immediately
  after the spawn, `01_file.c:4990`): the same two tables, and for every
  record whose `+0` is neither -1 nor the player's slot, `sub_41AD60(slot)` and
  `word_69BC80[slot] = -1`. Called from `evictSlot` (both halves,
  `sub_40D4A0`), from `sceneLoad` before the swap and from `sceneUnload`
  (scene half only, `sub_40BEC0(area, scene, 0)`).
* **`rebuildShown`** — `shown()` is derived now: slot 0's attached characters,
  then slot 1's, then the script-shown ones no table places. Called by the
  spawn, by 78/79, by `player.become` and by an eviction.
* **78 / 79 / `player.become`** now go through `showCharacter`/`hideCharacter`,
  which turn the spawned record's `attached` on or off. An id no table places
  keeps the old behaviour exactly — pushed onto `scriptShown_` — because the
  engine's handler could not attach it either (it gives up on a record whose
  actor index is -1) and a frontend still wants the body. The bit writes are
  untouched.
* `resetWorld` fills `actorSlots_` with -1 beside `objectSlotIds_`; `restart`
  clears `scriptShown_` beside `shown_`.

`spawn_probe <gamedata> <tables>`, one `key name value …` line per fact, in
`livezones_probe`'s shape (its `emit` helper copied, its intro run copied).

## 5. One sentence for `engine/README.md`'s Session coverage row

> `Actors_SpawnFromTables` runs at every area load and every `scene.load`, so
> both resident slots carry the characters their AREA and SCENE tables place —
> model, `.CTL` bank, position, facing, runtime slot and the `ObjectShown` bit
> that decides whether each is attached — and `shown()` is derived from them
> (7 spawned and 4 attached for the Impasse, `verify.py: engine spawn from tables`).

## 6. What stays labelled, and where the code differs from the engine

* **No model is loaded.** `Actor_LoadModel(slot, name + ".3DO", area)` and
  `Actor_LoadBankList` have no counterpart: the Session holds no geometry and
  no `.CTL` runtime instance per world character. The names are recorded
  (`model`, `bank`) and a frontend opens them — that is T20 / `omk-play.md` 41.
  So a placement naming an actor whose `.3DO` is missing would fault in the
  engine and is silent here.
* **No actor object, so `Actor_SetPlacement`'s side effects are absent.** The
  engine writes the position twice (`[58..60]` and `[61..63]`), the yaw at
  `[105]`, rebuilds the 3x3 at `+288`, calls `o3de_SetNodePos` and
  `SpatialIndex_Update`, and zeroes seven fields when the actor IS the player.
  The port keeps the placement as data on `Character`; nothing consumes the
  spatial index yet.
* **`freeActorSlots` does not model the player exception.** `sub_40BEC0` skips
  the record whose `+0` equals `Actor_Player()`'s slot, so the player's runtime
  entry is never handed back. The Session has no runtime slot for the player at
  all, so there is nothing here that exception would protect; labelled rather
  than invented.
* **A record whose actor id resolves to nothing** is skipped with its runtime
  slot still handed out (the engine takes the slot before the lookup and then
  faults reading `+144` off a null record). No shipped record does this — all
  nine ids in the probe resolve — but the difference is deliberate.
* **The truncation is applied on read, not written back.** `Area_Load`
  rewrites the chunk's own bytes; `readPlacements` converts each time from the
  raw file bytes, which cannot double-convert and gives the same values. Only
  record `+0` is written back into the chunk, which is what
  `Scene_FindObjectRecord`'s callers read.
* **`Actor_Attach`/`Actor_Detach` themselves** (0x0041CCA0 / 0x0041CDD0, the
  o3de tree link) are still just the `attached` flag; the render tree is the
  viewer's.

## 7. Found wrong on the way

1. **The issue's placement numbers are rounded, the engine's are truncated**
   (§1). `7605 -80 2980` / `358` → `7604 -79 2980` / `357`. Found only by
   reading `Area_Load`'s conversion loop after the probe disagreed with the
   brief by one unit in three fields at once — which is the signature of a
   rounding difference, not of a wrong layout.
2. **The issue names one call site; there are two.** It says
   "called once from `Area_TickLoad` case 5", and `readable/src/01_file.c:4815`'s
   banner says `@callers 1`. Opcode 71 `scene.load`'s handler (0x403950) calls
   it too, with `a3 = 0` — verified with `tools/asmfn.py --op 71`, and already
   quoted (unremarked) in `area.cpp`'s own `sceneLoad` comment as
   `call sub_40BB90 / sub_409FC0 ; its props and actors`. The handler is not in
   the decompilation under any name, which is why the banner's count is short:
   CLAUDE.md §1's "a direct call site is what makes a `proc` label" trap seen
   from the other side — here the *callee's* count is wrong because the
   *caller* was never recognised as code.
3. **The issue predicts `attached_ids 212,218,219,57` at the Impasse; playing
   there gives `212,218,219,49`.** Both are right: the first is the cold load
   the bits describe, the second is after the intro's scripts have run. The
   probe reports both, because a check that only pinned one would have looked
   like a failure of whichever run it was not built from.
