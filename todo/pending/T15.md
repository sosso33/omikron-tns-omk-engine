### 1a. The world hooks (T12 §6, adapted to T11's slots)

T12 wrote its `Hooks` against one `curArea_` and two writable copies. T11's Session
keeps the resident blocks as `ResidentSlot::areaChunk` / `sceneChunk` — vectors, so
they ARE the writable blocks the engine edits in place. The hooks read and write
`slots_[k].areaChunk` / `sceneChunk` directly through `props.h`; no copies.

* `Hooks::record(actor)` is `Actor_FindById` (0x0040B190): **row 0 then row 1**
  (`v2 = &dword_69BC40; ... v2 += 4`), the AREA table when `v2[2] >= 0` and the
  SCENE table when `v2[3] >= 0` — the IDS, not the block pointers.
  `Session::actorRecord` walked the SHOWN slot first until now; it is corrected to
  the same order (a difference only when both rows carry the same actor id).
* `Hooks::inObjectTable` is `Scene_FindObjectRecord`'s gate: 86/93 on an id the
  20-byte table does not name read garbage in the engine; the hook refuses.
* `loadProps(slot, area, scene)` is `Scene_LoadProps(area, scene, 1)` (0x00409FC0):
  for every prop record whose state has bit 0, the **first free** entry of
  `word_4E6CA0` takes the id and the record's `+0` takes the slot; bit 1 links it
  into the scene. Called where the engine calls it — `Area_TickLoad` case 5/6 (in
  `completeLoad`, before case 9's contexts) and after `Scene_Load` in `scene.load`
  (`sub_40BB90 / sub_409FC0`). `unloadProps` is `Scene_UnloadProps` (01_file.c:3955):
  `word_4E6CA0[rec+0] = -1` for every such record, at the eviction, at `scene.load`
  (the old scene) and at `scene.unload` — handed the IDS, so a block kept under bit 8
  (§1d) is not walked twice.
* `setHooks(&hooks_)` in `newContext`, which every creation site now funnels through
  (startup, message, zone).

### 1b. The live zones (T13 §3)

`Session` owns a `ZoneRegistry`. `zonesRegisterAll()` builds the two `omk::ResidentSlot`
rows from `slots_[k]` (ids and spans) and calls `registerAll`; the registry releases
the prompt slots whose zone no longer resolves (`detached()`), and the Session frees
every context whose `zoneId` no longer resolves — `Zones_RegisterAll`'s tail. It runs
where T11 already called it: case 9, the eviction, `scene.load`/`unload`, event 9, the
restart. Never per frame.

`frame()` is now `Game_Tick`'s order:

```
Script_Pump(1) step 1+2   pumpZoneSlots()        05_sys.c:2107
Script_Pump(1) step 3     runContext(i) x 32
Script_Pump(1) step 4     pumpTail()
                          tickCamera, scene tick, trackPlayer, transitionObjectEnded
Actors_TickAll            scanZonesNow()         05_sys.c:2178
```

and during a conversation: scene tick, `trackPlayer`, **`scanZonesNow()`**, the voice
clock. **T13's "the scan runs during a conversation" is confirmed, and by a different
mechanism than "no dialogue gate on the actor tick":** `Actors_TickAll` dispatches on
the player's `ACTOR_STATE`, and `Actor_ScanZones` is reached from `Actor_TickNpc`
(1, 11..14), **`Actor_TickDialogue` (16/17 — `return Actor_ScanZones(a1);` is its
last line)**, `Actor_TickUiHeld` (9) and `sub_466E70` (10); NOT from
`Actor_TickScxDriven` / `Actor_StartPendingScx` (4/5), the fight tick (2) or the
shoot tick (3/15). So the scan runs in a conversation and does **not** run while a
`scx.play.player*` program owns him — `trackPlayer()` now sets `playerDriven_` and the
scan gates on it. Cases 7 and 8 of `Game_HandleEvent` carry no dialogue gate either.

`pumpZoneSlots()` is `Script_Pump` steps 1 and 2 (§2 for step 2). The prompt slots'
`+0` pointers are kept Session-side (`promptCtx_[16]`) because the engine keys the
reuse arm and the actions on the POINTER, not the zone id: case 1's
`if (ctx && u16(ctx,42) == zoneId && u8(ctx,24) == 4) { u8(ctx,24) = 0; --u16(ctx,28); }`
is the zone re-armed while its free is still at the head of the FIFO, and the released
slot's `+0` is left dangling as the engine leaves it (the port clears it on every free
rather than read through a reused entry). An Activate does `++dword_4E61E0` before
`Script_QueueAction(ctx, 2)` and `++dword_4E6B20` on success; Leave and Free queue
unconditionally.

`scanZonesNow()` hands `playerPos_` / `playerYaw_` (degrees) to the registry and
applies event 8's camera as a cut (the last touch wins, one request block).

`Script_Pump` step 2, from the CLEAN text and the assembly (11025–11150):

```

    if (Actor_HeldObjectSlot(Actor_Player()) == -1) { if (dword_4E66B8) post message 26 }
    else if (state != 3 && state != 15) { dword_91068C = -1; sub_41C770(); }

dword_4E6C90 = 0;
```

**The dry-run marker is dead for message 26.** `dword_4E66B8` has exactly one reader
in the image (asm 11137, `cmp dword_4E66B8, ebx`), the `if` above, which sits inside
`!dword_4E61E0`. Its only store of 0 (11048, `mov dword_4E66B8, edi`) is adjacent to
`++dword_4E61E0` (11045–11049) with no branch between. So whenever the reader runs
the flag is still 1, and message 26 posts **iff the press arrived (a prompt slot was
taken — event 6's gate) and no slot in state 2 had an activate script**. `Script_Run`'s
result — the activate script dry-run hitting a "visible" opcode — cannot change it.
The port runs NO dry run; `pumpZoneSlots` counts Activate events (`ran`) and posts 26
through T2's `postMessage(26, -1)` when the count is 0. The sender: `evArgs[1]` is never
written in `Script_Pump` (only `mov [esp+20h+var_10], 1Ah`), so the engine passes stack
garbage; the port passes −1, labelled.

**What bit 0x10 IS, from the assembly** (every `or byte ptr [reg+28h], 10h` in the
handler range, mapped to the VM table): **24 handlers** — 46, 57, 58, 59, 61, 62, 63,
70, 73, 89, 90, 92, 94, 95, 96, 118, 119, 122, 123, 126, 129, 130, 138, 139. Issue 7's
list said "89–96": **91 and 93 do not set it** (checked with `asmfn.py --op 91/93`);
129 and 130 do, from the two unlabelled functions after 128's handler. Every one of
the 24 ORs it in **before** its `dword_6A05E0` dry-run test, and nothing in the image
clears it (`Script_NewContext` zeroes +40; no `and ... 0EFh` anywhere) — so it is a
sticky per-context "did something visible", and `Script_Run`'s
`while ((u8(ctx,40) & 0x10) == 0)` never loops on a context that has run anything.
The port sets it from the recorded calls (`visibleOp`, `Ctx::flags40`); no interpreter
change was needed, and `contextFlags(idx)` reports it (the deferred line reads 24).

The held-object path (`Script_RunToOpcode75`, `sub_41C770`) stays labelled: the
registry refuses the activate when `setHeldObject(true)`, and step 2's else-arm is a
