# The tables compiled into `Runtime 2.exe`

Generated by [`tools/exetables.py`](../tools/exetables.py). **Do not
hand-edit** — run the tool; `verify.py: exe tables` fails on a stale file.

## Why this directory exists

A replica engine asks the user for their own copy of the game and reads `gamedata/`.
These tables are not in `gamedata/` — they are `.data` and `.rdata` inside
`Runtime 2.exe` — so a build that expects the user's game files has nowhere to
get them. [`docs/RECONSTRUCTION.md`](../docs/RECONSTRUCTION.md) names this as
the one gap a level-C build hits, and deferred it on the grounds that lifting
early "only creates a second copy to drift". That reason expires when `engine/`
starts, and the drift is now covered by a check.

They are **facts about the game, not code** — tier 1 of that document's porting
plan, the tier that needs no CLEAN body — so nothing here transcribes an
instruction, and the no-original-assembly constraint is untouched.

**`vm_announce.json` has a different provenance from the rest.** The others
are read out of the executable's bytes; this one is derived from the
disassembly by `tools/vm_announce.py` — the section name each handler passes to
`Dbg_LogTagged`. It is here because a replica needs it as *data* for exactly
the reason the others are: a hand-written map inside `engine/` was wrong three
ways within an hour of being written — `scx.play` (57) and `music.play` (103)
announce **nothing**, and `scx.play.actor.wait` (60) announces the **actor**,
not the object. 49 handlers announce; the other 104 opcodes are silent, and
silence has to be read as silence rather than as a default.

Each file carries its own provenance, a prose `about`, and the checks that were
run when it was written.

## Two things a port must not get wrong

**The VM's operand lengths.** `vm_opcodes.json` has both `table_says` — the
executable's own second dword — and `length`, which is what a decoder must
actually use. ~~**17 of them disagree**~~ — **21 as of 2026-09-02** (62 last, from the corpus's own adjudication: 216 phantom instructions at 4 that vanish at 6 - `verify.py: engine: parking ops`), recovered
from the handlers' assembly and corpus-confirmed; a decoder that trusts the
table desynchronises on the world scripts. `corrected` flags the rows where
they differ, and the file itself is the count to trust: 16, 17, 42, 43, 44, 57,
58, 78, 80, 84, 103, 118, 119, 144, 146, 147, 148, 149, 150, 151.

The three added on 2026-09-02 are the same class of finding and none of them is
reachable from shipped data, which is exactly why the corpus had not caught
them: **16 `set.var.i32` reads 6 bytes, not the table's 5** (the handler at
`0x00402070` takes the variable through the shared fetch and then a 32-bit
literal; its own family settles it — 14 is 2+1 and 15 is 2+2, so 5 is not a
length any of the three shapes can produce), and **43 / 44 are 42's siblings**
at 4 and 6 bytes, named `case.i16` / `case.i32`, with **0 shipped sites each**.
A wrong length is only reachable by a file that does not ship — and a decoder
meeting one desynchronises from the label byte on, so they are recorded rather
than left to the corpus.

Two names in the file were also **wrong rather than missing**, and both were
settled against the image on 2026-09-02: op **93** is `actor.stat.set`, not
`hud.show_var` (both arms of `0x00404790` reach `Actor_SetProperty`; the HUD
flash is the player-only extra the old name was taken from), and ops **111 /
112** were **inverted** — 111 is `timer.stop`, 112 `timer.start`. The count of
named opcodes is **129**. See [`docs/SCRIPT_VM.md`](../docs/SCRIPT_VM.md) for
both derivations.

> `verify.py`'s `engine: scripts` docstring still narrates "the 17 corrected
> ones" while asserting the falsification count (77 slots) rather than the
> corrections' count, so it does not fail on this; the prose is stale and the
> file above is authoritative.

**Op 2's handler is not in `clean/_vmsummary.json`.** It reads 0 there, because
the extraction pass could not bound that block. The image says `0x00401B80`,
and the image is the authority — this is a case where lifting from the
executable *fills* a hole in a derived file rather than duplicating it.

## What is deliberately not here

`RECONSTRUCTION.md` listed the weapon stats among the compiled tables. It was
wrong: `Weapon_SlotForObject` indexes `IAM\GLOBAL +32`, which ships. So do the
fight-AI profiles (`.CTL` `+76`/`+80`) and the combination table
(`GLOBAL +12`). A replica reads those from the user's data like everything
else, and a copy here would be exactly the second copy the plan warned about.

## How each one is checked

A wrong base address yields plausible-looking numbers, so every table carries a
test its own data could fail:

* **camera presets — the table indexes itself.** Each row's `mode` field at
  `+36` equals its own row number, for 22 rows, and the 23rd reads 24909. Base
  *and* stride are pinned by the data with no external evidence. Mode 0 then
  reads −118.11 inches, which is 3.00 m exactly — the metric authoring every
  other engine constant shows.
* **ADPCM — two independent readings.** The 105 numbers come out byte-identical
  to the ones `tools/adp.py` transcribed by hand from `sub_483200`.
* **`tab_special_move` — terminated and consumed.** Three zero dwords end it at
  exactly 66 rows, and all 54 distinct move names the shipped `.CTL` files use
  resolve in it.
* **VM — cross-tool.** 152 of 153 handlers match `clean/_vmsummary.json`, built
  by a different tool from the disassembly; the 153rd is op 2 above.
* **key bindings — inside the producing function's code space.** A keyboard
  code must be a scan code 1..255, a mouse code a button 12..14, a joystick
  code its index plus 48 — the three spaces `Input_ReadOneControl` produces.
  41, 4 and 48 non-zero cells, none outside its own space.
